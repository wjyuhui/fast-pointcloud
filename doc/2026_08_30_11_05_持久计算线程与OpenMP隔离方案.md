# 持久计算线程与OpenMP隔离方案

> 本文用于交给 Cursor 实施。实现前必须先通读本文和当前源码，不要按旧版`OMP_PLACES + OMP_PROC_BIND=CLOSE`方案回退，也不要顺手修改PCL障碍物节点、RANSAC、BEV或V4算法内容。

## 一、逻辑方案

### 1.1 简洁方案

当前`cloud_workspace_node`使用单线程`rclcpp::spin()`，深度回调由进程主线程执行。深度回调直接进入`#pragma omp parallel`后，ROS主线程自动成为OpenMP tid0，并被当前手动亲和性代码固定到CPU列表第一项。虽然FastDDS等已经创建的线程仍为CPU0-7，但主线程不再是CPU0-7，未达到“OpenMP计算线程与ROS线程完全分离”的目标。

最终方案：

1. ROS深度回调只做输入校验、CameraInfo快照、将深度图`SharedPtr`写入容量为1的线程安全任务槽，然后立即返回。
2. 节点构造结束前创建一个持久计算协调线程；它只创建一次，节点析构时停止并`join()`。
3. 持久计算线程取出最新任务，负责TF查询、V2/V3/V4投影、局部点云合并、Voxel、`pcl::toROSMsg()`和`publish()`。
4. V3中只有持久计算线程调用OpenMP函数，因此它成为OpenMP tid0并绑定CPU列表第一项；其余libgomp worker绑定后续CPU。
5. ROS Executor主线程、TF2线程和FastDDS线程保持启动时的CPU0-7，不再进入OpenMP并行区。
6. 任务槽只保留一帧待处理任务。计算忙时，新帧覆盖旧的未处理帧，避免实时系统积压历史消息。
7. V2、V3、V4统一走同一个持久计算线程，避免三个版本使用不同线程架构。
8. 原`callback_p95`改为“深度回调接收任务到publish完成”的流水线耗时，包含队列等待；额外记录`queue_wait_p95`和丢帧数。

目标线程模型（V3四线程）：

```text
ROS Executor主线程                     → CPU0-7
TF2/FastDDS及其他非计算线程             → CPU0-7
持久计算协调线程/OpenMP tid0            → CPU4
libgomp OpenMP worker tid1/tid2/tid3   → CPU5/CPU6/CPU7
```

### 1.2 详细方案

#### 1.2.1 当前代码上下文

主要文件：

```text
src/rgbd_pcl/src/cloud_workspace_node.cpp
src/rgbd_pcl/CMakeLists.txt
src/rgbd_bringup/launch/perception.launch.py
src/rgbd_bringup/config/perception.yaml
```

当前入口：

```cpp
int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<CloudWorkspaceNode>());
  rclcpp::shutdown();
  return 0;
}
```

这是单线程Executor，`depthCallback()`由进程主线程执行。当前回调同步完成：

```text
CameraInfo检查
→ TF查询
→ V2/V3/V4投影
→ Voxel
→ PointCloud2转换
→ publish
→ 性能统计
```

V3投影函数`depthToWorkspaceOpenMP()`内部已有以下重要逻辑，必须保留：

```text
prepareOpenMPBuffers()
每线程独立CloudT
num_threads(requested_threads)
每线程连续行块划分
thread_local bound_compute_cpu
sched_setaffinity()手动绑定当前线程
一次性OMP_AFFINITY验证
并行区后按tid顺序合并局部点云
```

当前launch已经：

```text
不再传递OMP_PLACES
OpenMP模式设置OMP_PROC_BIND=FALSE
仅OpenMP启用时传递非空projection_openmp_cpus
```

Cursor不得恢复以下旧逻辑：

```python
'OMP_PLACES': projection_omp_places
'OMP_PROC_BIND': 'CLOSE'
```

也不得把`proc_bind(close)`重新加回OpenMP pragma。

#### 1.2.2 当前问题的准确边界

当前V3四线程结构：

```text
进程主线程 = ROS Executor线程 = depthCallback执行线程 = OpenMP tid0
```

`num_threads(4)`不是“主线程加4个worker”，而是：

```text
原ROS主线程/tid0 1个 + libgomp worker 3个 = 4个OpenMP线程
```

当前亲和性因此为：

```text
主线程/tid0 → CPU4
worker       → CPU5-7
其他ROS/FastDDS线程 → CPU0-7
```

这与原全局绑定仍有本质区别：全局绑定发生在线程创建前，会让ROS/FastDDS线程继承单核；当前手动绑定发生在第一帧OpenMP计算时，不会反向修改已经创建的线程。但如果验收目标要求主线程也保持CPU0-7，当前结构仍不满足。

#### 1.2.3 目标线程角色

引入一个进程内持久计算协调线程，线程只创建一次：

```text
线程A：ROS Executor主线程
  - CPU亲和性：保持外层默认CPU0-7
  - 职责：执行CameraInfo回调、Depth回调、提交任务
  - 禁止：直接调用V2/V3/V4投影和Voxel

线程B：持久计算协调线程
  - V3亲和性：projection_openmp_cpus[0]
  - V2/V4亲和性：projection_compute_cpu
  - 职责：TF、投影、Voxel、转换、publish、性能统计
  - V3身份：OpenMP primary tid0

线程C组：libgomp workers
  - 数量：projection_openmp_threads - 1
  - 亲和性：projection_openmp_cpus[1..N-1]
  - 职责：仅参与OpenMP投影并行区
```

四线程V3仍只有四个OpenMP计算线程：

```text
持久计算协调线程/tid0 1个 + libgomp worker 3个 = 4个
```

整个进程比当前方案多一个线程，因为ROS主线程不再兼任tid0。

#### 1.2.4 容量为1的最新帧任务槽

使用一个`std::optional<FrameJob>`作为唯一待处理槽，不使用无界`std::queue`。

任务结构至少包含：

```cpp
struct FrameJob
{
  sensor_msgs::msg::Image::SharedPtr depth;
  sensor_msgs::msg::CameraInfo camera_info;
  std::chrono::steady_clock::time_point pipeline_begin;
  uint64_t sequence{0};
};
```

必须携带`camera_info`快照，原因是当前`prepareWorkspaceInputs()`直接读取成员`camera_info_`。异步化后，CameraInfo回调可能写成员，而计算线程同时读取，形成C++数据竞争。不能只给深度图加锁却继续让计算线程读裸成员。

任务槽语义：

```text
计算线程空闲：新任务入槽并立即被取走
计算线程忙、槽为空：保存一帧待处理任务
计算线程忙、槽已有任务：新任务覆盖旧任务，dropped_pending_frames + 1
```

这样最多存在：

```text
1帧正在计算 + 1帧等待处理
```

不会积压几十帧旧数据。

#### 1.2.5 Depth回调职责

新的`depthCallback()`只能做以下事情：

```text
记录pipeline_begin
取得CameraInfo一致性快照
构造FrameJob（SharedPtr，不复制深度图data）
加job_mutex_写pending_job_
必要时覆盖旧pending并增加drop计数
解锁
notify_one()
立即返回
```

禁止在持有`job_mutex_`时：

```text
查询TF
执行投影
执行Voxel
转换消息
publish
日志输出大量内容
```

锁只保护任务槽和停止标志，临界区必须非常短。

#### 1.2.6 CameraInfo并发安全

增加独立`camera_info_mutex_`，不要复用任务槽锁，避免不必要的锁耦合。

CameraInfo回调：

```text
锁camera_info_mutex_
更新camera_info_
设置have_info_
解锁
```

Depth回调：

```text
锁camera_info_mutex_
若没有CameraInfo则解锁并节流告警后返回
复制camera_info_到局部变量
解锁
将局部快照放入FrameJob
```

计算线程之后只使用`job.camera_info`，禁止再读取`camera_info_`或`have_info_`。

#### 1.2.7 持久计算循环

计算线程执行`computeLoop()`：

```text
启动
→ 一次性绑定协调线程CPU
→ 等待条件变量
→ stop时退出
→ 从pending_job_移动任务到局部变量并清空槽
→ 解锁
→ 计算queue_wait_ms
→ processFrame(job)
→ 返回等待
```

条件变量必须使用谓词，防止虚假唤醒：

```cpp
job_cv_.wait(lock, [this]() {
  return stop_requested_ || pending_job_.has_value();
});
```

取出任务后立即解锁，整个处理过程不能持有任务槽锁。

每帧外层增加`try/catch`，避免一次异常导致持久线程静默退出或`std::terminate()`：

```text
捕获std::exception
记录节流错误
丢弃当前任务
继续等待下一帧
```

不要尝试从OpenMP并行区内部抛异常跨越pragma边界。

#### 1.2.8 完整处理链归属

将当前`depthCallback()`的重计算部分移动到`processFrame(const FrameJob & job)`，由持久计算线程调用：

```text
根据job.camera_info确定optical_frame
→ lookupTransformMatrix()
→ V2 Scalar / V3 OpenMP / V4 NEON
→ VoxelGrid
→ pcl::toROSMsg()
→ 设置header
→ cloud_pub_->publish()
→ recordTiming()
```

推荐将完整链路放在计算线程，不要只异步OpenMP后让ROS回调同步等待结果。否则ROS主线程仍被阻塞，线程隔离收益有限，并且需要额外的双向同步。

`tf2_ros::Buffer`允许从计算线程查询；`rclcpp::Publisher::publish()`也可从该持久线程调用。必须保证析构时先停止并join计算线程，再让Publisher和TF成员进入成员析构。

#### 1.2.9 V2/V3/V4统一性

三个模式必须都调用同一个`processFrame()`，只在投影函数处分支：

```text
V2：depthToWorkspaceScalar()
V3：depthToWorkspaceOpenMP()
V4：depthToWorkspaceNeon()
```

不要只给V3创建持久线程，而让V2/V4继续在ROS回调执行。否则：

```text
线程模型不一致
亲和性不一致
callback/pipeline指标定义不一致
版本性能对比不公平
```

增加统一计算协调CPU配置：

```text
projection_compute_cpu
```

规则：

```text
V3：launch自动使用projection_openmp_cpus[0]作为projection_compute_cpu
V2/V4：使用launch参数projection_compute_cpu，默认选择大核CPU7
```

V2/V4的持久计算线程因此也固定在一个明确大核上；ROS/FastDDS仍保持CPU0-7。

#### 1.2.10 亲和性生命周期

节点启动阶段必须保持：

```text
不设置OMP_PLACES
OMP_PROC_BIND=FALSE
```

建议cloud_workspace节点在所有模式都显式覆盖：

```python
'OMP_DYNAMIC': 'FALSE',
'OMP_PROC_BIND': 'FALSE',
```

避免用户终端遗留OpenMP环境污染V2/V4进程启动。

构造顺序：

```text
Node/TF成员构造
→ 参数声明和校验
→ 创建CameraInfo订阅、Depth订阅、Publisher
→ 输出启动日志
→ 构造函数最后启动compute_thread_
→ 构造结束后进入rclcpp::spin()
```

计算线程启动时绑定自身一次。它之后创建/唤醒OpenMP团队，现有手动绑定逻辑继续把每个team线程映射到目标CPU。

不要使用每帧“保存tid0 CPU0-7、绑定CPU4、结束后恢复CPU0-7”的方案。该方案在板端曾测得`core_p95`约15 ms，迁核与亲和性系统调用开销不可接受。

#### 1.2.11 性能统计定义

异步化后，ROS回调函数本身只负责入槽，其函数耗时不能再代表端到端处理。

保持历史字段可比性的建议：

```text
core_ms：投影函数开始到结束，保持原定义
voxel_ms：Voxel开始到结束，保持原定义
queue_wait_ms：FrameJob入槽时间到计算线程取出时间
callback_ms：pipeline_begin到publish返回，保留旧字段名但语义明确为流水线耗时
```

日志新增：

```text
queue_wait_p95
submitted_frames
processed_frames
dropped_pending_frames
```

也可以同时输出`pipeline_p95`，但如果保留`callback_p95`供现有表格使用，必须在日志和文档中注明其现在是“消息进入回调到publish完成”，而不是C++回调函数栈耗时。

所有性能样本容器只由计算线程写入；析构线程必须在join后读取和`logPerf()`，避免数据竞争。

#### 1.2.12 停止与析构顺序

当前析构只调用`logPerf()`。异步化后必须改成：

```text
1. 锁job_mutex_
2. stop_requested_=true
3. 清空pending_job_（停止时不再处理排队旧帧）
4. 解锁
5. job_cv_.notify_all()
6. compute_thread_.join()
7. join完成后再logPerf()
8. 析构函数体结束，Publisher/TF/Subscription等成员随后正常析构
```

如果计算线程正在处理一帧，析构可以等待当前帧完成；不能detach，也不能让线程在Node成员销毁后继续publish。

#### 1.2.13 不在本次修改范围内

Cursor不得把以下内容混入本次修改：

```text
6/8线程大小核加权分块或dynamic schedule
RANSAC OpenMP
NEON算法重写
ROS2组件化/intra-process
PCL obstacle节点线程模型
固定rosbag内容
V0/V1历史实现
参数动态更新
无锁队列
实时调度SCHED_FIFO
```

这些应分别评估，避免持久线程改造与算法变化同时发生，导致无法归因性能变化。

## 二、逻辑方案对应的代码方案

### 2.1 简洁方案

按以下顺序修改：

1. 在`cloud_workspace_node.cpp`增加线程、互斥量、条件变量、optional和atomic相关头文件。
2. 新增`FrameJob`、任务槽、CameraInfo锁、停止标志、持久线程和提交/处理/停止计数成员。
3. 参数增加`projection_compute_cpu`；V3使用OpenMP CPU列表首项，V2/V4使用该参数。
4. 构造函数先完成ROS实体创建，再在最后启动`compute_thread_`。
5. CameraInfo回调加锁；Depth回调改为容量1任务提交，不再执行TF、投影、Voxel和publish。
6. 新增`computeLoop()`和`processFrame()`，把当前Depth回调的完整处理链迁移过去。
7. `prepareWorkspaceInputs()`以及三个投影入口显式接收`const CameraInfo &`，彻底消除异步读取成员`camera_info_`的数据竞争。
8. 保留当前OpenMP每线程buffer、手动亲和性、`thread_local`一次绑定和一次性验证逻辑。
9. 析构函数先停止、notify、join，再输出性能统计。
10. launch新增/传递`projection_compute_cpu`，所有模式覆盖`OMP_PROC_BIND=FALSE`，继续禁止`OMP_PLACES`。
11. CMake显式链接`Threads::Threads`。
12. 编译后依次验证V2、V3、V4功能、亲和性、固定包性能、丢帧和连续启停。

### 2.2 详细方案

#### 2.2.1 需要新增的头文件

在`cloud_workspace_node.cpp`按现有排序加入：

```cpp
#include <atomic>
#include <condition_variable>
#include <mutex>
#include <optional>
#include <thread>
#include <utility>
```

不要删除当前OpenMP、NEON、`sched.h`、PCL、TF2相关头文件。

#### 2.2.2 FrameJob定义

建议在`CloudWorkspaceNode`私有区域、常量之后定义：

```cpp
struct FrameJob
{
  sensor_msgs::msg::Image::SharedPtr depth;
  sensor_msgs::msg::CameraInfo camera_info;
  std::chrono::steady_clock::time_point pipeline_begin;
  uint64_t sequence{0};
};
```

约束：

```text
depth必须是SharedPtr，禁止复制depth.data
camera_info必须是值快照
pipeline_begin必须在Depth回调入口记录
sequence用于日志和丢帧诊断，不参与ROS时间戳
```

#### 2.2.3 新增成员变量

在现有成员区加入并用注释分组：

```cpp
int projection_compute_cpu_{7};

std::mutex camera_info_mutex_;

std::mutex job_mutex_;
std::condition_variable job_cv_;
std::optional<FrameJob> pending_job_;
bool stop_requested_{false};  // 只在job_mutex_保护下访问
std::thread compute_thread_;

std::atomic<uint64_t> submitted_frames_{0};
std::atomic<uint64_t> processed_frames_{0};
std::atomic<uint64_t> dropped_pending_frames_{0};

std::vector<double> queue_wait_samples_;
```

如果所有计数都严格在同一锁下访问，可以不用atomic；但日志由计算线程、提交由Executor线程，使用atomic更直接。不要对同一个变量混用“有时加锁、有时atomic”的访问方式。

#### 2.2.4 参数声明和校验

构造函数新增：

```cpp
declare_parameter<int>("projection_compute_cpu", 7);
projection_compute_cpu_ = get_parameter("projection_compute_cpu").as_int();
```

校验：

```text
0 <= projection_compute_cpu_ < CPU_SETSIZE
V3时projection_openmp_cpus数量仍必须等于线程数
V3协调CPU最终必须取projection_openmp_cpus.front()
```

建议构造完成最终CPU：

```cpp
const int coordinator_cpu = projection_enable_openmp_
  ? projection_openmp_cpus_.front()
  : projection_compute_cpu_;
```

不要在V3中额外要求用户手写两个必须相等的参数；launch直接把CPU列表首项作为协调CPU，避免配置自相矛盾。

#### 2.2.5 CameraInfo回调修改

当前匿名lambda直接写成员：

```cpp
camera_info_ = *msg;
have_info_ = true;
```

改为：

```cpp
{
  std::lock_guard<std::mutex> lock(camera_info_mutex_);
  camera_info_ = *msg;
  have_info_ = true;
}
```

不要用`job_mutex_`保护CameraInfo。

#### 2.2.6 Depth回调伪代码

将当前重回调替换为提交逻辑：

```cpp
void depthCallback(const sensor_msgs::msg::Image::SharedPtr msg)
{
  const auto pipeline_begin = std::chrono::steady_clock::now();

  sensor_msgs::msg::CameraInfo camera_info_snapshot;
  {
    std::lock_guard<std::mutex> lock(camera_info_mutex_);
    if (!have_info_) {
      // 锁外或确保节流日志不会形成复杂锁依赖
      return;
    }
    camera_info_snapshot = camera_info_;
  }

  FrameJob job;
  job.depth = msg;
  job.camera_info = std::move(camera_info_snapshot);
  job.pipeline_begin = pipeline_begin;
  job.sequence = submitted_frames_.fetch_add(1) + 1;

  {
    std::lock_guard<std::mutex> lock(job_mutex_);
    if (stop_requested_) {
      return;
    }
    if (pending_job_.has_value()) {
      dropped_pending_frames_.fetch_add(1);
    }
    pending_job_ = std::move(job);
  }

  job_cv_.notify_one();
}
```

告警处理建议：先在锁内得到`have_info`状态，释放锁后再调用`RCLCPP_WARN_THROTTLE`，避免日志路径持有CameraInfo锁。

#### 2.2.7 computeLoop伪代码

```cpp
void computeLoop()
{
  const int coordinator_cpu = projection_enable_openmp_
    ? projection_openmp_cpus_.front()
    : projection_compute_cpu_;

  if (!bindCurrentThreadToCpu(coordinator_cpu)) {
    // 记录错误并将运行标为无效；不要静默继续生成正式性能数据
  }

  RCLCPP_INFO(
    get_logger(),
    "COMPUTE_THREAD target_cpu=%d actual_cpu=%d",
    coordinator_cpu, sched_getcpu());

  while (true) {
    FrameJob job;
    {
      std::unique_lock<std::mutex> lock(job_mutex_);
      job_cv_.wait(lock, [this]() {
        return stop_requested_ || pending_job_.has_value();
      });

      if (stop_requested_) {
        return;
      }

      job = std::move(*pending_job_);
      pending_job_.reset();
    }

    const auto compute_begin = std::chrono::steady_clock::now();
    const double queue_wait_ms =
      std::chrono::duration<double, std::milli>(
        compute_begin - job.pipeline_begin).count();

    try {
      if (processFrame(job, queue_wait_ms)) {
        processed_frames_.fetch_add(1);
      }
    } catch (const std::exception & ex) {
      RCLCPP_ERROR_THROTTLE(
        get_logger(), *get_clock(), 2000,
        "Compute thread frame failed: %s", ex.what());
    }
  }
}
```

说明：如果协调线程在`computeLoop()`开头已绑定首个CPU，当前OpenMP并行区的tid0会再次执行一次`thread_local`首次绑定到同一CPU。这只发生一次且位于warmup前，功能正确。可后续重构公共绑定助手，但本次优先保证清晰和正确，不要为了消除一次重复系统调用大改OpenMP代码。

#### 2.2.8 线程绑定助手

新增返回错误状态的助手，不要在计算线程中直接抛出导致线程退出：

```cpp
bool bindCurrentThreadToCpu(int cpu, int & error)
{
  cpu_set_t mask;
  CPU_ZERO(&mask);
  CPU_SET(cpu, &mask);

  if (sched_setaffinity(0, sizeof(mask), &mask) != 0) {
    error = errno;
    return false;
  }

  error = 0;
  return true;
}
```

协调线程绑定失败时：

```text
启动日志明确报target、actual、errno
omp_affinity_valid_=false或新增compute_affinity_valid_=false
最终PERF日志标记affinity_ok=false
```

不要自动退回不绑定后仍输出`affinity_ok=true`。

#### 2.2.9 processFrame迁移

将当前`depthCallback()`中从`optical_frame`计算到`recordTiming()`的代码迁移到：

```text
camera_info_           → job.camera_info
```

#### 2.2.12 构造与析构实现

构造函数要求：


启动代码：


析构代码顺序：

```cpp
~CloudWorkspaceNode() override
{
  {
    std::lock_guard<std::mutex> lock(job_mutex_);
    stop_requested_ = true;
    pending_job_.reset();
  }
  job_cv_.notify_all();

  }
}
```

#### 2.2.21 性能验收与结果解释
