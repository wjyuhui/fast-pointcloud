# V3 OpenMP大小核绑定与回归测试方案

## 一、逻辑方案

### 1.1 简洁方案

V3需要把“OpenMP线程数”和“OpenMP线程运行在哪些CPU核心”作为两个独立变量控制：

- `projection_openmp_threads`只控制并行区线程数量；
- `OMP_PLACES`明确给出允许OpenMP使用的逻辑CPU编号；
- `OMP_PROC_BIND=CLOSE`和并行区的`proc_bind(close)`要求线程紧密绑定到这些places；
- 不使用`taskset ros2 launch ...`包住完整launch，避免相机、YOLO、PCL、BEV等无关进程一起被限制；
- 不在每帧中调用`pthread_setaffinity_np()`保存、绑定和恢复亲和性，避免系统调用开销污染`core_p95`；
- 启动后的第一次OpenMP并行区记录每个`tid`对应的`place`和实际CPU，证明绑定真实生效；
- 按1大核、2大核、4大核、2小核+4大核、全8核完成矩阵测试，固定rosbag、频率策略、测量帧数和温度条件。

根据板端`lscpu`结果，本项目暂定：

- CPU 0～3：小核，最高频率1.8 GHz；
- CPU 4～7：大核，最高频率2.304 GHz。

测试矩阵：

| 模式 | `projection_openmp_threads` | `OMP_PLACES` | 目的 |
|---|---:|---|---|
| V3-1T | 1 | `{7}` | 测OpenMP固定开销 |
| V3-2T | 2 | `{6},{7}` | 测双大核并行收益 |
| V3-4T | 4 | `{4},{5},{6},{7}` | 测四大核主要候选配置 |
| V3-6T | 6 | `{2},{3},{4},{5},{6},{7}` | 测大小核混合后的负载不均 |
| V3-8T | 8 | `{0},{1},{2},{3},{4},{5},{6},{7}` | 测全核并发和带宽竞争 |

### 1.2 详细方案

#### 1.2.1 当前问题

当前C++并行区已经使用：

```cpp
#pragma omp parallel num_threads(requested_threads) default(none) shared(...)
```

其中`num_threads(requested_threads)`只决定OpenMP团队请求多少个线程，`requested_threads=1 actual_threads=1`只能证明实际创建了1个线程，不能证明该线程运行在大核。

当前`perception.launch.py`也没有为`cloud_workspace_node`设置OpenMP亲和性环境，因此此前未显式设置亲和性的结果必须标记为“CPU未绑定”，不能直接写成“1/大核”或“4/大核”。

#### 1.2.2 绑定层次

V3采用以下三层控制：

1. 线程数量：

   ```text
   projection_openmp_threads=N
   ```

   由ROS2参数进入`num_threads(requested_threads)`。

2. 可用CPU集合：

   ```text
   OMP_PLACES={4},{5},{6},{7}
   ```

   每个花括号定义一个OpenMP place，显式指定逻辑CPU编号。

3. 绑定策略：

   ```text
   OMP_PROC_BIND=CLOSE
   proc_bind(close)
   ```

   `CLOSE`表示线程优先使用相邻places。环境变量给出进程内OpenMP运行时的默认策略，并行区子句明确该并行区采用的策略。

`OMP_DYNAMIC=FALSE`同时固定，禁止OpenMP运行时根据负载自行减少团队规模。C++中的`omp_set_dynamic(0)`继续保留，两者功能重复但能够让代码约束和实验环境记录保持一致。

#### 1.2.3 为什么不使用完整launch级taskset

以下命令不作为正式测试方式：

```bash
taskset -c 4-7 ros2 launch rgbd_bringup perception.launch.py
```

因为`ros2 launch`启动的相机、静态TF、点云、障碍物、BEV和YOLO进程都会继承CPU集合，导致传感器发布、其他节点调度和系统竞争状态一起发生变化，无法把结果归因到V3反投影OpenMP。

`additional_env`只添加到`cloud_workspace_node`对应的`Node`动作，使OpenMP配置不会传播到其他节点。

#### 1.2.4 “只绑定OpenMP代码”的边界

`OMP_PLACES/OMP_PROC_BIND`控制的是OpenMP团队，不会像`taskset`一样先把整个launch的所有进程限制在同一CPU集合。但是OpenMP团队的主线程就是进入并行区的ROS回调线程，具体OpenMP运行时可能让主线程在离开并行区后继续保持亲和性。因此该方案属于“OpenMP运行时级绑定”，不能宣称亲和性只在并行区的几行循环代码执行期间存在。

如果必须做到严格的“进入并行区前保存亲和性、计算时绑定、退出前恢复”，可以在每个线程中使用：

```text
pthread_getaffinity_np()
pthread_setaffinity_np()
计算
pthread_setaffinity_np()恢复
```

但这会在每帧、每个线程产生亲和性系统调用。当前核心计算仅约1.5～5 ms，这部分开销会污染`core_p95`，因此不作为正式性能版本，只能作为一次性的诊断实验。

#### 1.2.5 大小核实验公平性

正式测试统一满足：

- 使用同一Release构建；
- V3打开OpenMP、关闭手写NEON；
- 使用同一固定rosbag或完全相同的相机输入场景；
- 保持`depth_stride`、ROI、TF、VoxelGrid等参数不变；
- 固定CPU governor、频率策略和OpenMP等待策略；
- 每组先预热，再采集1000帧；
- 每种配置至少独立运行3次，结果记录各次p95并采用中位结果；
- 每组测试前让温度回落到统一范围；
- 同时记录`core_p95`、`voxel_p95`、`callback_p95`、CPU占用、温度、requested threads、actual threads和实际CPU映射。

1、2、4线程只使用大核；6线程固定为CPU 2～7，即2小核+4大核；8线程使用全部核心。当前代码按线程ID等分采样行数，混合大小核时每个线程得到近似相同的行数，小核更慢，可能成为并行区末尾barrier的决定者。因此6线程或8线程不一定比4大核更快，这正是V3异构平台测试需要展示的结论。

#### 1.2.6 V2基线的公平比较

现有V2 Scalar结果如果没有固定CPU，只能作为历史基线。要严格计算V3-1T相对V2的OpenMP固定开销，需要补充一组“V2 Scalar固定CPU7”和“V3-1T固定CPU7”的受控对照。

由于V2没有OpenMP团队，`OMP_PLACES`不会约束V2标量循环。该对照可以单独把`cloud_workspace_node`固定到CPU7运行，且V2和V3-1T必须使用完全相同的节点级亲和性。该对照用于分析Core固定开销，不与OpenMP-only绑定矩阵中的Callback结论混写。

当前已有结果：

```text
V2 Scalar core_p95=4.272 ms
V3-1T未确认绑定 core_p95=4.937 ms
```

其名义Core加速比为：

```text
4.272 / 4.937 = 0.87x
```

在重新完成受控绑定前，该结果应标注“未确认CPU亲和性”，不能作为最终的1大核数据。

#### 1.2.7 绑定验证

不能只依赖`requested_threads`和`actual_threads`判断绑定。启动后第一次进入OpenMP并行区时，应为每个线程采集：

- `omp_get_thread_num()`：OpenMP线程编号；
- `omp_get_num_threads()`：实际团队规模；
- `omp_get_proc_bind()`：当前绑定策略；
- `omp_get_num_places()`：运行时识别到的places数量；
- `omp_get_place_num()`：当前线程所在place；
- `sched_getcpu()`：采样时实际运行的Linux逻辑CPU。

并行区内只写入预分配的小数组，不调用ROS日志。退出并行区后由主线程输出一次，例如：

```text
OMP_AFFINITY requested=4 actual=4 places=4 bind=close
OMP_AFFINITY tid=0 place=0 cpu=4
OMP_AFFINITY tid=1 place=1 cpu=5
OMP_AFFINITY tid=2 place=2 cpu=6
OMP_AFFINITY tid=3 place=3 cpu=7
```

日志只输出一次并发生在预热阶段，不进入正式1000帧统计，避免逐帧日志干扰性能。

#### 1.2.8 结果判定

每组必须先确认：

1. `actual_threads == requested_threads`；
2. 每个线程的实际CPU属于本组`OMP_PLACES`；
3. 1/2/4线程没有落到CPU 0～3；
4. 测试期间没有明显降频或热节流；
5. 日志标签、线程数、CPU集合和结果表一致。

最终结果表：

| 模式 | 线程/CPU集合 | Core p95 | Voxel p95 | Callback p95 | Core加速比 | CPU% | 温度 |
|---|---|---:|---:|---:|---:|---:|---:|
| V2 Scalar | 受控基线/CPU7 | * | * | * | 1.00x | * | * |
| V3 OMP | 1/CPU7大核 | * | * | * | * | * | * |
| V3 OMP | 2/CPU6-7大核 | * | * | * | * | * | * |
| V3 OMP | 4/CPU4-7大核 | * | * | * | * | * | * |
| V3 OMP | 6/CPU2-7混合 | * | * | * | * | * | * |
| V3 OMP | 8/CPU0-7全核 | * | * | * | * | * | * |

## 二、代码方案

### 2.1 简洁方案

计划修改三个位置：

1. `src/rgbd_bringup/launch/perception.launch.py`
   - 新增OpenMP线程数、CPU places和V3模式启动参数；
   - 仅对`cloud_workspace_node`增加`additional_env`；
   - 通过参数覆盖YAML，避免每组实验手工改源码。
2. `src/rgbd_pcl/src/cloud_workspace_node.cpp`
   - 在现有OpenMP指令上新增`proc_bind(close)`；
   - 保持现有`num_threads`、`default(none)`和`shared(...)`不变；
   - 增加一次性线程CPU映射采集和并行区外日志。
3. `src/rgbd_bringup/config/perception.yaml`
   - 保留默认安全配置；
   - 正式V3测试由launch参数覆盖为OpenMP开启、NEON关闭。

不修改反投影、TF、ROI、线程局部点云、合并和计时边界，不加入每帧`pthread_setaffinity_np()`。

### 2.2 详细方案

#### 2.2.1 Launch参数设计

在`generate_launch_description()`中新增：

```python
DeclareLaunchArgument('projection_enable_openmp', default_value='false')
DeclareLaunchArgument('projection_openmp_threads', default_value='1')
DeclareLaunchArgument('projection_enable_neon', default_value='true')
DeclareLaunchArgument('projection_omp_places', default_value='{7}')
```

在`launch_setup()`中读取并校验：

- `projection_openmp_threads`转换为整数，范围保持1～16；
- OpenMP开启时，`projection_omp_places`不能为空；
- V3中OpenMP和NEON不能同时开启；
- places数量应与请求线程数一致，避免一个place上安排多个线程造成结果歧义。

为`cloud_workspace_node`增加参数覆盖：

```python
parameters=[
    params_file,
    {
        'projection_enable_openmp': projection_enable_openmp,
        'projection_openmp_threads': projection_openmp_threads,
        'projection_enable_neon': projection_enable_neon,
    },
]
```

OpenMP开启时为该节点增加：

```python
additional_env={
    'OMP_DYNAMIC': 'FALSE',
    'OMP_PLACES': projection_omp_places,
    'OMP_PROC_BIND': 'CLOSE',
}
```

这里不增加`prefix='taskset ...'`，避免把整个节点的所有阶段预先限制到CPU集合。需要做V2与V3-1T节点级严格对照时，另设独立测试参数，不混入V3主矩阵。

#### 2.2.2 OpenMP指令修改

现有指令：

```cpp
#pragma omp parallel num_threads(requested_threads) default(none) \
    shared(...)
```

计划改为：

```cpp
#pragma omp parallel num_threads(requested_threads) proc_bind(close) default(none) \
    shared(...)
```

本次只新增`proc_bind(close)`：

- `num_threads(requested_threads)`：现有设置，控制请求线程数；
- `proc_bind(close)`：新增设置，要求当前团队紧密绑定到places；
- `default(none)`：现有设置，要求显式声明变量数据属性；
- `shared(...)`：现有设置，现有变量列表原样保留，不用替换为省略号。

#### 2.2.3 一次性亲和性日志

新增只用于验证的小型成员缓存，例如：

```cpp
std::vector<int> omp_cpu_by_thread_;
std::vector<int> omp_place_by_thread_;
bool omp_affinity_logged_{false};
```

缓存在线程数确定后预分配。第一次并行区中，每个线程只写自己的下标：

```cpp
cpu_by_thread[tid] = sched_getcpu();
place_by_thread[tid] = omp_get_place_num();
```

并行区退出后统一检查并输出。禁止在并行区内直接调用`RCLCPP_INFO`，禁止逐帧打印，禁止在正式测量段重复分配数组。

如果某线程实际CPU不属于预期集合，输出WARN并将该轮结果判为无效；不在性能代码中自动迁移线程或静默纠正，以免隐藏配置错误。

#### 2.2.4 配置互斥与标签

继续保留现有约束：

```text
projection_enable_openmp=true
projection_enable_neon=false
```

V3日志继续使用：

```text
PERF V3_OMP requested_threads=N actual_threads=N ...
```

建议额外在启动日志记录原始places字符串或规范化CPU集合，使性能日志与测试表能够一一对应。不要把只设置了线程数但未验证CPU映射的结果标记为“大核”。

#### 2.2.5 启动方式

完成上述launch参数开发后，测试命令设计为：

```bash
ros2 launch rgbd_bringup perception.launch.py \
  projection_enable_openmp:=true \
  projection_openmp_threads:=4 \
  projection_enable_neon:=false \
  projection_omp_places:='{4},{5},{6},{7}'
```

其他组只替换线程数和places字符串。花括号参数使用单引号，避免Shell解释。

若工程不是通过`colcon build --symlink-install`构建，修改Python launch后需要重新构建`rgbd_bringup`并重新执行：

```bash
source install/setup.bash
```

#### 2.2.6 开发与验证顺序

1. 先增加launch参数和`additional_env`，确认配置只进入`cloud_workspace_node`；
2. 增加`proc_bind(close)`并完成编译；
3. 增加一次性CPU/place日志；
4. 用4线程、CPU4～7做功能验证，确认线程映射；
5. 运行1、2、4、6、8线程矩阵；
6. 补做V2与V3-1T同核受控对照；
7. 汇总三次独立运行的p95、CPU和温度；
8. 只有验证通过的数据才写入最终简历表格。

#### 2.2.7 验收标准

- 构建无错误、无新增编译警告；
- V2、V3、V4模式互斥关系正确；
- V3请求线程数等于实际线程数；
- 每组线程仅落在其声明的CPU集合；
- 亲和性日志只输出一次，不影响1000帧正式统计；
- 不修改现有反投影数学结果和点云输出顺序约定之外的语义；
- 同一输入下点云数量和几何结果与V2处于既定容差内；
- 结果表完整记录CPU集合，不能只记录线程数；
- 4大核、6混合和8全核的差异能够由负载均衡、barrier等待、内存带宽和温度数据解释。
