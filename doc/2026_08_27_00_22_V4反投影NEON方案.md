# V4 反投影 NEON 方案

- 时间：2026-08-27 00:22（Asia/Shanghai）
- 目标平台：RK3588S / AArch64
- 当前范围：V4 = V2 标量融合链路 + NEON，OpenMP 关闭
- 本文档性质：实现前方案，不包含源码修改

## 一、逻辑方案

### 1.1 简洁方案

V4 保留 V2 的“深度读取→反投影→Transform→ROI 过滤→写入点云”单遍融合思路，新增一条独立的单线程 NEON 路径：

```text
每帧深度图
  → 准备输入并校验射线缓存
  → 按深度编码选择 uint16_t 或 float 路径
  → 按采样行遍历
  → 每次取 4 个采样深度
  → NEON 并行完成 4 点反投影、Transform 和过滤
  → 按有效掩码以 lane 0→3 顺序写入点云
  → 每行剩余 0～3 点调用原标量函数处理
```

保留三条可独立回归的路径：

| 版本 | OpenMP | NEON | 处理函数 |
|---|---:|---:|---|
| V2 | 关 | 关 | `depthToWorkspaceScalar()` |
| V3 | 开 | 关 | `depthToWorkspaceOpenMP()` |
| V4 | 关 | 开 | `depthToWorkspaceNeon()` |

当前 V4 不支持 OpenMP 与 NEON 同时开启，避免在尚未验证单线程 NEON 收益前引入大小核调度、线程私有点云及合并开销。

### 1.2 详细方案

#### 1.2.1 版本边界和对照关系

1. `depthToWorkspaceScalar()` 保持纯标量，作为正确性和性能基线。
2. `depthToWorkspaceOpenMP()` 保持“标量内核 + 行分块并行”，作为 V3 对照组。
3. 新增 `depthToWorkspaceNeon()`，仅使用一个工作线程，将内层列遍历改为每次 4 点的 SIMD 批处理。
4. 新增 `tryAppendPointsNeon4()`，作为四点 NEON 内核；原 `tryAppendPoint()` 保留，用于 V2/V3 和 V4 每行的标量尾部。
5. 性能数据必须用三条独立路径测量，不通过函数名与实际实现不一致的“标量函数内部再分发 NEON”方式实现。

#### 1.2.2 每帧数据流

`depthToWorkspaceNeon()` 首先复用 `prepareWorkspaceInputs()`，完成：

- 深度图宽高、步长与编码校验；
- `depth_stride` 获取；
- ROI 和深度范围参数获取；
- Transform 矩阵拆分；
- 根据宽高、stride 和相机内参检查或重建 `ray_x_`/`ray_y_` 缓存；
- 区分 `16UC1`/`mono16` 与 `32FC1`。

不预先构建整幅 `x/y/z` 中间数组。每个四点批次直接从当前深度行与射线缓存取数，立即完成反投影、Transform、ROI 过滤和输出，避免额外整幅遍历与中间内存流量。

#### 1.2.3 行列遍历和 stride 映射

采样缓存坐标与原图坐标的映射为：

```text
v = vi * stride
u = ui * stride
```

同一批的四个点为：

```text
采样列：ui, ui+1, ui+2, ui+3
原图列：u, u+stride, u+2*stride, u+3*stride
ray_x： ray_x[ui ... ui+3]
ray_y： ray_y[vi] 广播到 4 个 lane
```

外层按 `vi` 遍历采样行，内层主循环使用：

```cpp
for (; ui + 3 < sampled_cols; ui += 4) {
  tryAppendPointsNeon4(...);
}
```

该条件保证一批内存在四个合法采样点。主循环结束后，剩余 0～3 点通过 `tryAppendPoint()` 处理，保证任意图像宽度和 stride 下不越界、不丢点。

#### 1.2.4 两种深度编码

`is_u16` 判断放在整帧遍历外，不进入内层热循环。

- `16UC1`/`mono16`：每批读取 4 个 `uint16_t`，转换为 `float32x4_t`，再乘 `0.001f` 将毫米转换为米。
- `32FC1`：每批读取 4 个 `float`，深度默认已以米为单位，不进行尺度转换。

两条路径的深度加载不同，但后续反投影、Transform、有效性判断、ROI 过滤和点云写入逻辑共用。

#### 1.2.5 第一版深度加载策略

`ray_x_` 是已按 stride 生成的采样缓存，`ray_x[ui ... ui+3]` 连续，可以直接向量加载。

原始深度行不同。当默认 `stride=4` 时，四个深度位于 `row[u]`、`row[u+4]`、`row[u+8]`、`row[u+12]`，不能用普通连续加载代替。

第一版采用通用 gather：按 stride 标量读取四个深度到小型局部数组，再加载为 NEON 向量。该方案优先保证任意 stride 和宽度的正确性。

若 Profiling 证明 gather 成为主要瓶颈，第二阶段再增加 `stride==1` 连续加载和 `stride==4` 交错加载特化。交错加载会额外读取采样点之间的原图元素，其向量循环边界必须按“整块加载不越过当前行末尾”判断，不能仅依赖 `ui + 3 < sampled_cols`。

#### 1.2.6 四路 NEON 计算

第一版使用 `float32x4_t`，一次并行处理四点。点云输出 `pcl::PointXYZ` 本身为 float，Transform 系数在每帧进入 NEON 路径时从 double 转为 float 一次，不在热循环中重复转换。

反投影与 Transform 可以代数融合为：

```text
x_target = z * (r00 * ray_x + r01 * ray_y + r02) + tx
y_target = z * (r10 * ray_x + r11 * ray_y + r12) + ty
z_target = z * (r20 * ray_x + r21 * ray_y + r22) + tz
```

这与先生成 `x_camera/y_camera/z_camera` 再进行矩阵乘法的数学意义一致，但减少中间向量，适合 AArch64 NEON FMA。

#### 1.2.7 有效性与 ROI 掩码

每批为四个 lane 生成掩码：

```text
depth_valid = finite(z) AND z >= zmin AND z <= zmax
roi_valid   = x_target >= xmin AND x_target <= xmax
              AND z_target >= zmin_roi AND z_target <= zmax_roi
valid       = depth_valid AND roi_valid
```

`finite(z)` 应与原 `std::isfinite()` 语义对齐，不只依赖上下界比较间接排除无穷大。无效 lane 可继续参与无分支向量计算，但最终不得写入点云。

#### 1.2.8 点云写入和顺序

AArch64 NEON 不提供适合本场景的通用压缩存储。第一版采用“向量计算 + 标量压缩写入”：

1. 将四路 `x_target/y_target/z_target` 和有效掩码写入 16 字节对齐的局部数组。
2. 按 lane 0、1、2、3 顺序检查掩码。
3. 仅对有效 lane 构造 `PointT` 并 `push_back()`。

`cloud_roi` 在进入循环前按最大采样点数 `reserve()`，避免热循环中扩容。按 lane 顺序写入可保持与标量版一致的行主序点顺序，便于逐点回归。

#### 1.2.9 数值精度策略

V2 当前使用 double Transform 中间计算后转 float，V4 四路 NEON 拟使用 float 系数和 FMA，因此不承诺比特级一致。验收时使用：

- 同帧输出点数差；
- 按顺序对齐后的 XYZ 最大绝对误差与 p95 误差；
- ROI 边界附近的成员差异；
- 下游 voxel 输出点数与障碍物结果差异。

若边界差异超过系统允许范围，再评估两路 `float64x2_t` 或调整标量参照计算精度；不在没有实测的情况下预先牺牲四路 SIMD 吞吐。

#### 1.2.10 平台与编译边界

NEON 头文件、向量类型和 intrinsic 仅在 AArch64/NEON 编译条件下可见。x86 开发环境应仍能编译 V2/V3；如在不支持的平台开启 NEON，启动时给出明确错误，不静默伪装成 V4 标签运行标量路径。

AArch64 架构本身包含 Advanced SIMD，不使用 AArch32 的 `-mfpu=neon` 选项。正式性能对比必须使用一致的 Release 优化等级，并保留实际编译命令和产物信息。

#### 1.2.11 自动向量化检查

手写 NEON 前先对 V2 内循环做自动向量化审计，符合 P4 的项目计划：

1. 使用 GCC 向量化报告检查已向量化和未向量化循环。
2. 检查 AArch64 汇编，确认 V2 是否已生成 SIMD/FMA 指令。
3. 记录阻碍自动向量化的因素，预期包括：深度 stride gather、`std::isfinite`、多级条件 return、变长有效点 `push_back()` 和 PCL AoS 布局。
4. 手写 NEON 版完成后再次检查汇编，确认关键计算确实保留为四路向量指令，没有因函数边界或类型转换退化为标量。

#### 1.2.12 正确性与性能验收

正确性覆盖：

- `16UC1`、`mono16`、`32FC1`；
- stride 为 1、2、4 及不能整除宽高的尺寸；
- 每行采样列数对 4 的余数为 0、1、2、3；
- u16 中的 0 和边界深度；
- float 中的 NaN、正负 Inf、正常值和边界值；
- ROI 内外以及恰好位于上下界的点；
- 输出点的行主序顺序和点云元信息。

性能验收使用同一固定 rosbag、同一 RK3588S 运行环境和同一 Release 构建，分别运行 V2 Scalar 与 V4 NEON。统计至少包括：

- `core_ms` 的 p50/p95/p99；
- `callback_ms` 的 p50/p95/p99；
- 平均帧率与丢帧率；
- CPU 占用和内存占用；
- V4 相对 V2 的加速比；
- 芯片温度、频率与是否发生降频。

预热帧、采样帧数、CPU 绑定和调频策略必须一致。NEON 的价值以板端实测为准，不以 intrinsic 数量作为完成标准。

## 二、逻辑方案对应的代码方案

### 2.1 简洁方案

预计代码结构：

```text
depthCallback()
  ├─ depthToWorkspaceScalar()       // V2，原样保留
  ├─ depthToWorkspaceOpenMP()       // V3，原样保留
  └─ depthToWorkspaceNeon()         // V4，新增
       ├─ tryAppendPointsNeon4()    // 主体，每次 4 点
       └─ tryAppendPoint()          // 每行尾部 0～3 点
```

代码改动点限定为：

1. 增加 AArch64 NEON 条件编译。
2. 增加 NEON 参数结构与四点内核。
3. 增加 `depthToWorkspaceNeon()`。
4. 修改启动配置校验和 `depthCallback()` 三路分发。
5. 增加 `PERF V4_NEON` 日志标识。
6. 不改写原 V2/V3 内循环，不删除原有注释。

### 2.2 详细方案

#### 2.2.1 条件编译

文件头部仅在支持时引入 NEON：

```cpp
#if defined(__aarch64__) && defined(__ARM_NEON)
#include <arm_neon.h>
#define RGBD_PCL_HAS_NEON 1
#else
#define RGBD_PCL_HAS_NEON 0
#endif
```

实际实现时可改用 CMake `target_compile_definitions()` 生成宏，但必须保证 x86 不解析 `float32x4_t` 和 NEON intrinsic。

#### 2.2.2 NEON 参数结构

在匿名命名空间增加只读参数包：

```cpp
struct NeonWorkspaceParams
{
  float zmin;
  float zmax;
  float xmin;
  float xmax;
  float zmin_roi;
  float zmax_roi;

  float r00, r01, r02, tx;
  float r10, r11, r12, ty;
  float r20, r21, r22, tz;
};
```

该结构在 `depthToWorkspaceNeon()` 每帧构造一次，内循环以 `const NeonWorkspaceParams &` 传入，避免继续扩大单点函数式的长参数列表。

#### 2.2.3 `tryAppendPointsNeon4()` 接口分层

对两种深度类型使用同名重载：

```cpp
inline void tryAppendPointsNeon4(
  CloudT & cloud,
  const uint16_t * row,
  size_t ui,
  size_t vi,
  int stride,
  const float * ray_x,
  const float * ray_y,
  const NeonWorkspaceParams & params);

inline void tryAppendPointsNeon4(
  CloudT & cloud,
  const float * row,
  size_t ui,
  size_t vi,
  int stride,
  const float * ray_x,
  const float * ray_y,
  const NeonWorkspaceParams & params);
```

两个重载只在深度读取和毫米转米方面不同。可再使用一个仅在本翻译单元可见的共用内核：

```cpp
inline void appendTransformedPointsNeon4(
  CloudT & cloud,
  float32x4_t z,
  size_t ui,
  size_t vi,
  const float * ray_x,
  const float * ray_y,
  const NeonWorkspaceParams & params);
```

第一版先依赖编译器正常内联，通过生成汇编确认；不在没有证据时直接增加 `always_inline` 强制属性。

#### 2.2.4 u16 四点加载

逻辑伪代码：

```cpp
const size_t u = ui * static_cast<size_t>(stride);

alignas(16) uint32_t depth_values[4] = {
  row[u],
  row[u + static_cast<size_t>(stride)],
  row[u + 2U * static_cast<size_t>(stride)],
  row[u + 3U * static_cast<size_t>(stride)]
};

const uint32x4_t raw = vld1q_u32(depth_values);
const float32x4_t z = vmulq_n_f32(vcvtq_f32_u32(raw), 0.001f);
appendTransformedPointsNeon4(...);
```

实现时可比较“先收集为 u16 再扩展”与“直接收集为 u32”的汇编和性能，选择板端实测更好的形式。

#### 2.2.5 float 四点加载

逻辑伪代码：

```cpp
const size_t u = ui * static_cast<size_t>(stride);

alignas(16) float depth_values[4] = {
  row[u],
  row[u + static_cast<size_t>(stride)],
  row[u + 2U * static_cast<size_t>(stride)],
  row[u + 3U * static_cast<size_t>(stride)]
};

const float32x4_t z = vld1q_f32(depth_values);
appendTransformedPointsNeon4(...);
```

这里的四个标量读取是有意识的第一版通用方案，不应误改为从 `row + u` 直接连续加载。

#### 2.2.6 共用四点计算内核

逻辑伪代码：

```cpp
const float32x4_t ray_x_vec = vld1q_f32(ray_x + ui);
const float32x4_t ray_y_vec = vdupq_n_f32(ray_y[vi]);

const float32x4_t x_direction =
  r00 * ray_x_vec + r01 * ray_y_vec + r02;
const float32x4_t y_direction =
  r10 * ray_x_vec + r11 * ray_y_vec + r12;
const float32x4_t z_direction =
  r20 * ray_x_vec + r21 * ray_y_vec + r22;

const float32x4_t x_target = z * x_direction + tx;
const float32x4_t y_target = z * y_direction + ty;
const float32x4_t z_target = z * z_direction + tz;

const uint32x4_t valid_mask =
  finite_mask
  & depth_range_mask
  & x_roi_mask
  & z_roi_mask;
```

实际代码使用 `vmulq_f32`、`vfmaq_*`、`vcgeq_f32`、`vcleq_f32`、`vandq_u32` 等 AArch64 intrinsic，并以生成汇编为准检查乘加数量。

#### 2.2.7 标量压缩写入

逻辑伪代码：

```cpp
alignas(16) float xs[4];
alignas(16) float ys[4];
alignas(16) float zs[4];
alignas(16) uint32_t valid[4];

vst1q_f32(xs, x_target);
vst1q_f32(ys, y_target);
vst1q_f32(zs, z_target);
vst1q_u32(valid, valid_mask);

for (size_t lane = 0; lane < 4; ++lane) {
  if (valid[lane] != 0U) {
    PointT p;
    p.x = xs[lane];
    p.y = ys[lane];
    p.z = zs[lane];
    cloud.push_back(p);
  }
}
```

若该部分在 Profiling 中成为瓶颈，再评估 16 种四位掩码的查表压缩或直接预扩容后索引写入；第一版优先保持清晰和可验证。

#### 2.2.8 `depthToWorkspaceNeon()` 伪代码

```cpp
bool depthToWorkspaceNeon(
  const sensor_msgs::msg::Image & depth,
  const Eigen::Affine3d & transform,
  CloudT & cloud_roi)
{
  // 与标量路径相同：准备参数、检查编码、确保射线缓存有效
  if (!prepareWorkspaceInputs(...)) {
    return false;
  }

  const size_t sampled_rows = ray_y_.size();
  const size_t sampled_cols = ray_x_.size();
  if (sampled_rows == 0 || sampled_cols == 0) {
    return false;
  }

  const float * ray_x = ray_x_.data();
  const float * ray_y = ray_y_.data();
  const NeonWorkspaceParams params{/* 每帧构造一次 */};

  cloud_roi.clear();
  cloud_roi.reserve(sampled_rows * sampled_cols);

  if (is_u16) {
    for (size_t vi = 0; vi < sampled_rows; ++vi) {
      const int v = static_cast<int>(vi) * stride;
      const auto * row = reinterpret_cast<const uint16_t *>(
        depth.data.data() + static_cast<size_t>(v) * depth.step);

      size_t ui = 0;
      for (; ui + 3 < sampled_cols; ui += 4) {
        tryAppendPointsNeon4(
          cloud_roi, row, ui, vi, stride, ray_x, ray_y, params);
      }

      for (; ui < sampled_cols; ++ui) {
        const int u = static_cast<int>(ui) * stride;
        tryAppendPoint(
          cloud_roi, static_cast<float>(row[u]) * 0.001f,
          ui, vi, ray_x, ray_y, /* 原标量参数 */);
      }
    }
  } else {
    for (size_t vi = 0; vi < sampled_rows; ++vi) {
      const int v = static_cast<int>(vi) * stride;
      const auto * row = reinterpret_cast<const float *>(
        depth.data.data() + static_cast<size_t>(v) * depth.step);

      size_t ui = 0;
      for (; ui + 3 < sampled_cols; ui += 4) {
        tryAppendPointsNeon4(
          cloud_roi, row, ui, vi, stride, ray_x, ray_y, params);
      }

      for (; ui < sampled_cols; ++ui) {
        const int u = static_cast<int>(ui) * stride;
        tryAppendPoint(
          cloud_roi, row[u], ui, vi, ray_x, ray_y,
          /* 原标量参数 */);
      }
    }
  }

  cloud_roi.width = cloud_roi.size();
  cloud_roi.height = 1;
  cloud_roi.is_dense = true;
  return !cloud_roi.empty();
}
```

`is_u16` 放在行列循环外，因此每帧只做一次编码分支。

#### 2.2.9 入口分发和配置校验

启动时校验：

```cpp
if (projection_enable_openmp_ && projection_enable_neon_) {
  throw std::invalid_argument(
    "V4 does not support projection OpenMP and NEON at the same time");
}

#if !RGBD_PCL_HAS_NEON
if (projection_enable_neon_) {
  throw std::invalid_argument(
    "projection_enable_neon=true requires an AArch64 NEON build");
}
#endif
```

每帧入口分发：

```cpp
bool ok = false;
if (projection_enable_openmp_) {
  ok = depthToWorkspaceOpenMP(...);
} else if (projection_enable_neon_) {
  ok = depthToWorkspaceNeon(...);
} else {
  ok = depthToWorkspaceScalar(...);
}
```

分支只在每帧入口执行一次，不在每点或每四点的内循环中检查 NEON 开关。

#### 2.2.10 性能日志

`logPerf()` 根据路径输出可区分标签：

```text
PERF V2_SCALAR
PERF V3_OMP
PERF V4_NEON
```

V4 日志至少保留 `samples/core_p95/voxel_p95/callback_p95`，后续回归工具再统一扩展 p50/p99、丢帧率、CPU 和内存数据。

#### 2.2.11 实施顺序

1. 生成 V2 自动向量化报告和 AArch64 汇编基线。
2. 加入平台宏、参数结构和编码分支的四点加载。
3. 实现共用 NEON 计算内核和标量压缩写入。
4. 实现 `depthToWorkspaceNeon()` 及每行标量尾部。
5. 增加三路分发、配置互斥和 V4 日志。
6. 在 x86 上验证非 NEON 路径仍可编译。
7. 在 RK3588S 上完成 Release 编译、汇编审计和正确性对比。
8. 使用固定 rosbag 完成 V2/V4 性能回归，再决定是否开发 stride 特化加载或掩码压缩优化。

#### 2.2.12 完成标准

V4 反投影 NEON 不以“源码中出现 NEON intrinsic”为完成，而以以下条件同时满足为准：

- V2/V3 原路径功能和性能回归无异常；
- V4 支持现有三种深度编码语义；
- 任意合法宽高与 stride 不越界、不丢尾点；
- NaN/Inf、深度范围和 ROI 语义与 V2 对齐；
- 数值误差与边界成员差异有明确测试结果；
- 汇编确认四路计算未退化为标量；
- RK3588S 固定数据集上得到可复现的 p95 结果和加速比；
- 性能收益能够抵消 gather、掩码压缩和 PCL AoS 写入开销。
