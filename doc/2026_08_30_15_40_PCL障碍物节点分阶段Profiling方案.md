# PCL 障碍物节点分阶段 Profiling 方案

目标：在不改变 `pcl_obstacle_node` 现有算法、参数和发布结果的前提下，建立可重复的分阶段性能统计，定位 RANSAC、KdTree、欧式聚类、点云转换和发布准备等环节的真实热点，为后续 OpenMP、NEON 和数据结构优化提供证据。

# 一、逻辑方案

## 1. 简洁方案

对 `pcl_obstacle_node` 的一次点云回调拆成以下阶段，并分别记录 p50、p95、p99：

1. PointCloud2 转 PCL；
2. SOR，可选；
3. 近地候选扫描；
4. RANSAC 模型搜索；
5. 地面和障碍物提取，或高度分割回退；
6. 地面、障碍物点云转 PointCloud2 与 publish 调用；
7. KdTree 构建；
8. Euclidean Cluster 搜索；
9. 聚类索引复制成独立点云；
10. bbox/center 统计与消息构造；
11. 障碍物和 Marker 的 publish 调用；
12. 完整 callback。

每帧同时记录输入点数、近地点数、地面点数、障碍物点数、聚类数和处理路径。RANSAC 成功、RANSAC 失败回退、近地点不足回退、直接高度分割必须分开统计，禁止混成一个 p95。前 30 个成功帧预热，之后每 1000 帧输出一条汇总日志，避免逐帧日志污染结果。

## 2. 详细方案



### 2.1 Profiling 的边界

本轮只增加观测能力，不修改以下内容：

- 不替换 PCL RANSAC；
- 不修改 RANSAC 阈值和迭代次数；
- 不修改近地候选判定逻辑；
- 不修改高度分割回退条件；
- 不修改 KdTree 和 EuclideanClusterExtraction 参数；
- 不加入 OpenMP 或 NEON；
- 不改变发布话题、消息内容和 QoS；
- 不顺手做容器复用、reserve 调整或算法融合。

这样得到的数据才是当前 PCL 实现的可信热点基线。后续每项优化都与该基线比较。

### 2.2 阶段定义和口径


| 指标                         | 起点                         | 终点                                | 说明                                    |
| -------------------------- | -------------------------- | --------------------------------- | ------------------------------------- |
| `from_ros_ms`              | 进入 `pcl::fromROSMsg` 前     | 返回后                               | 输入 PointCloud2 反序列化和 PCL 点云构造         |
| `sor_ms`                   | SOR 开始前                    | `sor.filter()` 返回后                | SOR 关闭时不纳入 SOR 样本，不记录伪造的 0 ms         |
| `near_ground_scan_ms`      | 遍历输入点统计近地点前                | 统计完成后                             | 只有 RANSAC 路径记录                        |
| `ransac_ms`                | `seg.segment()` 前          | 返回后                               | 只表示 PCL 模型搜索；不得包含候选扫描和 ExtractIndices |
| `ground_extract_ms`        | 创建/配置 ExtractIndices 前     | ground、obstacles 两次 filter 完成后    | RANSAC 成功时记录                          |
| `height_split_ms`          | `splitByHeight()` 前        | 返回后                               | 直接 height 或任何 fallback 路径记录           |
| `ground_total_ms`          | `segmentGround()` 调用前      | 返回后                               | 方便观察整个地面分割模块，同时保留内部细分                 |
| `cloud_to_ros_ms`          | 两个 `pcl::toROSMsg` 前       | 两个转换完成后                           | 地面和障碍物点云转换总耗时                         |
| `cloud_publish_call_ms`    | 两个点云 `publish()` 前         | 两次调用返回后                           | 只是发布 API 调用耗时，不等价于 DDS 端到端传输耗时        |
| `kdtree_ms`                | 创建/设置 KdTree 前             | `setInputCloud()` 返回后             | KdTree 建立阶段                           |
| `cluster_extract_ms`       | `ec.extract()` 前           | 返回后                               | 邻域搜索和聚类索引生成，是聚类主要候选热点                 |
| `cluster_materialize_ms`   | 遍历 `cluster_indices` 前     | 独立聚类点云构造完成后                       | 索引到点云的复制和分配                           |
| `cluster_total_ms`         | `euclideanCluster()` 前     | 返回后                               | KdTree、extract、materialize 总和         |
| `bbox_message_ms`          | `publishObstacles()` 构造消息前 | ObstacleArray 和 MarkerArray 构造完成后 | 包括 bbox、center、消息填充，不包括 publish 调用    |
| `obstacle_publish_call_ms` | 发布 ObstacleArray 前         | MarkerArray publish 返回后           | 两个发布 API 调用耗时                         |
| `callback_ms`              | `cloudCallback()` 入口       | 最后一次 publish 返回                   | 当前节点本次回调的完整软件流水线耗时                    |


计时统一使用 `std::chrono::steady_clock`。禁止使用 ROS 时间或消息 header 时间计算本机执行耗时，因为 rosbag 循环、时间戳回跳和 `/clock` 都会污染结果。

### 2.3 处理路径必须分开

当前 `segmentGround()` 至少存在四种路径：

1. `ground_method=height`：直接高度分割；
2. `ground_method=ransac`，但近地点数不足：`too_few_near_ground` 回退；
3. RANSAC 执行后无有效模型或内点不足：`ransac_failed` 回退；
4. RANSAC 成功：提取 ground 和 obstacles。

每帧记录一个枚举值 `ground_path`。窗口汇总必须输出每种路径的帧数和占比，例如：

```text
ground_paths ransac_ok=920 too_few=60 ransac_failed=20 direct_height=0
```

RANSAC 的 p50/p95/p99 只使用真正执行过 `seg.segment()` 的帧；`ground_extract_ms` 只统计 RANSAC 成功帧；`height_split_ms` 只统计进入高度分割的帧。不能用 0 补齐未执行阶段，否则 p95 会失真。

此前固定重场景包曾多次出现 `Too few near-ground points (26)`。如果正式窗口中大部分帧走 fallback，则该窗口只能评价高度分割，不能用来决定是否优化 RANSAC。应先寻找能持续触发有效地面 RANSAC 的固定场景，再做 RANSAC 优化评测。

### 2.4 同时记录工作量

耗时必须与数据规模一起输出，否则不同场景不可比较。每个统计窗口至少输出：

- `input_points`：输入点数 p50/p95；
- `near_ground_points`：近地点数 p50/p95；
- `ground_points`：地面点数 p50/p95；
- `obstacle_points`：障碍物点数 p50/p95；
- `cluster_candidates`：`ec.extract()` 返回的原始聚类数；
- `published_clusters`：受 `max_clusters` 限制后的发布聚类数；
- `clustered_points`：进入最终独立聚类点云的总点数；
- `empty_input_frames`、`failed_frames`；
- 各 ground path 的次数；
- 统计窗口的样本数。

对耗时阶段使用毫秒，对点数使用整数分位数。第一版不必记录每个聚类的分布文件，只输出窗口汇总，避免磁盘 I/O 干扰。

### 2.5 统计规则

- 默认预热：30 个完成回调；
- 默认测量窗口：1000 个完成回调；
- 输出：p50、p95、p99；
- 可选输出 max，但 max 只用于发现异常，不作为加速比主指标；
- 阶段样本使用独立 vector，未执行阶段不追加样本；
- 排序和分位数计算仅在窗口结束后执行一次；
- 窗口完成后 clear 容器但保留 capacity；
- 不逐帧 INFO；现有 WARN 保持节流；
- Profiling 关闭时只保留极小的条件判断开销；
- 正式 V2/V3/V4 对比必须使用相同包、相同参数、相同 CPU 亲和性、相同 governor 和相近温度。

建议日志分成三行，避免单行过长：

```text
PERF PCL samples=1000 callback_p50=... callback_p95=... callback_p99=...
PERF PCL_STAGE from_ros_p95=... ground_total_p95=... ransac_p95=... kdtree_p95=... cluster_extract_p95=...
PERF PCL_WORK input_pts_p95=... obstacle_pts_p95=... clusters_p95=... ransac_ok=... too_few=... ransac_failed=...
```



### 2.6 如何根据结果选择优化对象

第一轮只看同一固定场景的 p95 和 p99：

- `ransac_ms` 最大且 RANSAC 成功占比高：优先规划批量点面距离和内点统计的 OpenMP/NEON 重构；
- `cluster_extract_ms` 最大：优先调整输入规模、聚类算法和数据结构，不强行套 NEON；
- `kdtree_ms` 最大：研究树复用条件、输入点数和空间索引替代方案；
- `cluster_materialize_ms` 或 `bbox_message_ms` 较高：考虑基于索引直接统计 bbox/center，减少聚类点云复制；
- `from_ros_ms`、`cloud_to_ros_ms` 较高：归入 ROS2 数据流优化，评估组件化和 intra-process；
- `height_split_ms` 较高但 RANSAC 很少执行：先解决评测场景不匹配，不能据此宣布 RANSAC 已优化；
- 某阶段小于约 0.5 ms 且占 callback 很低：一般不作为主要 OpenMP/NEON 目标。



# 二、代码方案



## 1. 简洁方案

主要修改 `/home/cat/fast-pointcloud/src/rgbd_pcl/src/pcl_obstacle_node.cpp`：

1. 增加 `GroundPath`、`FrameProfile` 和窗口统计结构；
2. 在现有函数边界插入 `steady_clock` 计时；
3. 给 `segmentGround()`、`euclideanCluster()`、发布辅助函数增加可选的 Profiling 输出参数；
4. 保持所有原算法代码、执行顺序和现有注释不变；
5. 每帧结束时提交一次样本，每 1000 帧计算分位数并输出；
6. 在 `/home/cat/fast-pointcloud/src/rgbd_bringup/config/perception.yaml` 增加 Profiling 开关、预热帧数和窗口帧数；
7. 不增加新依赖，不修改消息定义，不修改 CMake，除非实现阶段编译证明确实需要。



## 2. 详细方案



### 2.1 新增参数

在 `pcl_obstacle_node` 参数区增加：

```yaml
profiling_enable: true
profiling_warmup_frames: 30
profiling_window_frames: 1000
```

参数语义：

- `profiling_enable=false`：不保存阶段样本，不输出 PERF；
- `profiling_warmup_frames`：跳过启动、DDS 建连、内存首次分配和缓存冷启动；
- `profiling_window_frames`：每个汇总窗口的完成回调数。

不建议第一版增加十几个阶段开关。统一开关更容易保证测试口径一致。

### 2.2 数据结构

在类的 private 区增加类似结构，名称可以按项目风格调整：

```cpp
enum class GroundPath
{
  kDirectHeight,
  kTooFewNearGround,
  kRansacFailed,
  kRansacOk
};

struct FrameProfile
{
  double from_ros_ms{0.0};
  double sor_ms{0.0};
  double near_ground_scan_ms{0.0};
  double ransac_ms{0.0};
  double ground_extract_ms{0.0};
  double height_split_ms{0.0};
  double ground_total_ms{0.0};
  double cloud_to_ros_ms{0.0};
  double cloud_publish_call_ms{0.0};
  double kdtree_ms{0.0};
  double cluster_extract_ms{0.0};
  double cluster_materialize_ms{0.0};
  double cluster_total_ms{0.0};
  double bbox_message_ms{0.0};
  double obstacle_publish_call_ms{0.0};
  double callback_ms{0.0};

  size_t input_points{0};
  size_t near_ground_points{0};
  size_t ground_points{0};
  size_t obstacle_points{0};
  size_t cluster_candidates{0};
  size_t published_clusters{0};
  size_t clustered_points{0};

  bool sor_executed{false};
  bool ransac_executed{false};
  bool ground_extract_executed{false};
  bool height_split_executed{false};
  GroundPath ground_path{GroundPath::kDirectHeight};
};
```

不要为了省代码而把“未执行阶段”当成 0 ms 样本。提交窗口统计时根据布尔字段决定是否追加对应 vector。

窗口统计可以使用一个 `ProfilingWindow` 结构，内部为每个耗时阶段的 `std::vector<double>`、点数 vector、路径计数和失败计数。构造时按 `profiling_window_frames` reserve。

### 2.3 `cloudCallback()` 的改动位置

保持现有处理顺序：

```text
fromROSMsg
→ 可选 SOR
→ segmentGround
→ 发布 ground/obstacles 点云
→ euclideanCluster
→ publishObstacles
```

具体做法：

1. callback 入口创建 `FrameProfile frame_profile` 和 `callback_begin`；
2. 包围 `pcl::fromROSMsg()`，填写 `from_ros_ms` 和 `input_points`；
3. SOR 开启时包围完整的 SOR 配置与 `filter()`，设置 `sor_executed=true`；
4. 包围 `segmentGround()` 得到 `ground_total_ms`，并把 `FrameProfile*` 传入函数填写内部阶段；
5. 分别统计 ground、obstacles 点数；
6. 不能继续只调用两次不可拆分的 `publishCloud()`。辅助函数应返回“转换耗时”和“publish 调用耗时”，两次结果累加到同一帧；
7. 包围 `euclideanCluster()` 得到 `cluster_total_ms`，内部填写三个子阶段；
8. `publishObstacles()` 内部分开统计消息构造和 publish 调用；
9. 最后一次 publish 返回后填写 `callback_ms`；
10. 调用 `recordProfile(frame_profile)`；
11. 空输入帧单独计数后返回，不混入成功回调耗时窗口。



### 2.4 `segmentGround()` 的改动位置

函数签名建议增加可选指针：

```cpp
void segmentGround(
  const CloudT::Ptr & input,
  CloudT::Ptr & obstacles,
  CloudT::Ptr & ground,
  FrameProfile * profile);
```

`profile == nullptr` 时正常执行原算法，不记录数据。

内部计时点：

- `ground_method == "height"`：设置 `kDirectHeight`，包围 `splitByHeight()`；
- near-ground 遍历：包围现有 for 循环，并记录 `near_ground`；
- near-ground 不足：设置 `kTooFewNearGround`，单独包围 fallback 的 `splitByHeight()`；
- `seg.segment()`：只包围这一行，设置 `ransac_executed=true`；
- RANSAC 内点不足：设置 `kRansacFailed`，包围 fallback；
- RANSAC 成功：设置 `kRansacOk`，包围两次 `ExtractIndices::filter()`，设置 `ground_extract_executed=true`。

保留当前 WARN、参数读取、模型类型、阈值和原有注释。不要在本次改动中修订 RANSAC 实现。

### 2.5 `euclideanCluster()` 的改动位置

函数签名建议变成：

```cpp
std::vector<CloudT::Ptr> euclideanCluster(
  const CloudT::Ptr & obstacles,
  FrameProfile * profile);
```

内部拆分：

1. `kdtree_ms`：从创建 KdTree 到 `tree->setInputCloud()` 返回；
2. PCL 聚类器的轻量参数配置不必单列，可以计入 `cluster_extract_ms`，但所有版本必须保持相同边界；
3. `cluster_extract_ms`：重点包围 `ec.extract(cluster_indices)`；
4. `cluster_candidates`：记录 `cluster_indices.size()`；
5. `cluster_materialize_ms`：包围当前 `for (indices)`、reserve、逐点复制和 push_back；
6. `published_clusters`：记录受 `max_clusters` 限制后的 `out.size()`；
7. `clustered_points`：累加复制到各独立聚类点云的点数。

不要在 Profiling 阶段取消独立聚类点云、直接基于 indices 计算 bbox。那属于后续 Data-oriented 优化，必须保留为单独版本和单独收益。

### 2.6 发布阶段的拆分

当前 `publishCloud()` 同时包含 `pcl::toROSMsg()` 和 `publish()`。建议返回一个小结构：

```cpp
struct PublishTiming
{
  double conversion_ms{0.0};
  double publish_call_ms{0.0};
};
```

两次点云发布的 conversion 和 publish_call 分别累加。必须在日志或文档中注明：`publish()` 返回只表示消息交给 rclcpp/rmw，不表示订阅者已经收到。

`publishObstacles()` 同理：

- 从创建并填充 ObstacleArray/MarkerArray 到构造完成，计入 `bbox_message_ms`；
- 两个 `publish()` 调用计入 `obstacle_publish_call_ms`。

不要把 bbox/center 循环和 publish 合成一个指标，否则后续无法判断 NEON 归约是否值得。

### 2.7 分位数工具和日志

增加通用分位数函数，支持 p50、p95、p99。为避免每个分位数复制并排序一次，可在窗口结束时对每个阶段复制一次、排序一次，然后读取三个位置。

建议实现：

```cpp
struct Percentiles
{
  double p50{0.0};
  double p95{0.0};
  double p99{0.0};
};
```

如果阶段样本为空，日志输出 `n=0`，不要输出看似有效的 `0.000 ms`。每个条件阶段同时输出样本数，例如：

```text
ransac_n=940 ransac_p50=... ransac_p95=... ransac_p99=...
height_split_n=60 height_split_p95=...
```

首个窗口在预热 30 帧后收集 1000 个完整回调。之后每 1000 帧继续输出，便于观察温升和调频后的窗口变化，而不是只打印一次。

### 2.8 配置文件和启动方式

在 `/home/cat/fast-pointcloud/src/rgbd_bringup/config/perception.yaml` 的 `pcl_obstacle_node.ros__parameters` 中添加三个 Profiling 参数即可。当前 launch 已经向节点加载该 YAML，第一版不必增加 launch 参数。

编译后沿用现有启动命令。V2 标量投影示例：

```bash
  projection_enable_openmp:=false \

```

播放固定包时只发布必要话题，避免 14.7 GiB 原包中的彩色图干扰：


正式 RANSAC Profiling 前必须先观察 `ground_paths`。如果 `too_few` 占多数，应更换为包含足够地面的固定片段；不要为了获得好看的 RANSAC 耗时临时降低 `min_ground`，因为那会改变算法语义和结果质量。

### 2.9 验证与验收标准

实现后按以下顺序验证：

1. Release 编译通过，无新增警告；
2. Profiling 关闭时，所有输出话题、点数和可视化行为与修改前一致；
3. Profiling 开启时，输出仍与修改前一致；
4. `callback_ms` 应大于等于主要顺序阶段之和，允许存在参数读取、对象构造等未单列开销；
5. `ground_total_ms` 应覆盖对应路径内部阶段，但不要求严格等于子阶段之和；
6. `cluster_total_ms` 应覆盖 KdTree、extract、materialize；
7. `ransac_n + direct/fallback` 的路径计数应与窗口样本数一致；
8. 未执行 RANSAC 的帧不进入 `ransac_ms` 分位数；
9. 连续输出至少两个 1000 帧窗口，确认 p95/p99 与点数分布基本稳定；
10. 根据最大耗时阶段形成下一份优化方案，本轮不直接实现 OpenMP 或 NEON。

最终交付物应包括：修改前后的功能一致性说明、两个稳定窗口的完整 PERF 日志、各阶段耗时占比表，以及“为什么选择下一个优化算子”的数据结论。
