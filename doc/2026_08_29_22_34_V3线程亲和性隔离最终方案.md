# V3 OpenMP线程亲和性隔离最终方案

## 一、逻辑方案

### 1.1 简洁方案

V3不再使用进程启动环境中的`OMP_PLACES + OMP_PROC_BIND=CLOSE`。这组设置会在节点启动阶段绑定初始线程，导致之后创建的ROS、TF2和FastDDS线程继承第一个CPU的单核亲和性。

最终方案如下：

1. 节点启动时显式设置`OMP_PROC_BIND=FALSE`，不让libgomp自动绑定初始线程。
2. launch仍接收`projection_omp_places`，但只把它解析为目标CPU数组传给节点。
3. OpenMP并行区中使用`sched_setaffinity()`逐线程绑定，且每个OpenMP线程只在首次参与时绑定一次。
4. OpenMP tid0就是ROS回调主线程，因此它绑定CPU列表中的第一个CPU；其他OpenMP worker依次绑定后续CPU。
5. ROS、TF2、FastDDS等非OpenMP线程不调用亲和性接口，继续保留CPU0-7亲和性。
6. CPU列表必须把大核放在前面，使tid0以及并行区后的Voxel、消息转换和publish运行在大核上。

最终4大核验证结果：

```text
OpenMP tid0/ROS回调主线程：CPU4
OpenMP worker：CPU5、CPU6、CPU7
其他ROS/TF2/FastDDS线程：CPU0-7

PERF V3_OMP requested_threads=4 actual_threads=4 affinity_ok=true samples=1000
core_p95=0.616 ms voxel_p95=2.126 ms callback_p95=3.014 ms
```

### 1.2 详细方案

#### 1.2.1 原问题与根因

旧方案在launch中设置：

```text
OMP_PLACES={0},{1},...,{7}
OMP_PROC_BIND=CLOSE
```

OpenMP团队总线程数包含原来的回调线程。例如8线程实际是：

```text
tid0：原ROS回调线程
tid1～tid7：7个libgomp工作线程
```

libgomp在进程启动阶段把初始线程放到第一个place。ROS、TF2、FastDDS随后创建的线程继承该单核掩码，于是出现：

```text
主线程及全部ROS/FastDDS线程：CPU0
OpenMP worker：CPU1～7
```

这使publish与FastDDS内部线程竞争同一个CPU，V3曾出现约14.7 ms的固定callback额外开销。

#### 1.2.2 最终隔离边界

最终方案只修改OpenMP团队线程：

```text
进程启动
  ├─ 不启用libgomp全局绑定
  ├─ ROS/TF2/FastDDS线程正常创建，允许CPU0-7
  └─ 第一次进入OpenMP并行区
       ├─ tid0绑定目标CPU列表第1项
       ├─ tid1绑定目标CPU列表第2项
       └─ 其余worker依次绑定
```

当前节点使用单线程`rclcpp::spin()`，ROS实体和FastDDS线程都在第一帧OpenMP计算前创建完成。之后只对OpenMP团队调用`sched_setaffinity()`，所以非OpenMP线程不受影响。

边界说明：tid0同时是ROS回调主线程和OpenMP计算线程，它属于需要绑定的计算团队，因此会固定在CPU列表第一个CPU；“不影响其他线程”指ROS/TF2/FastDDS的其他线程保持原来的CPU0-7亲和性。

#### 1.2.3 为什么不采用每帧保存和恢复tid0

曾实测以下方案：

```text
每帧进入并行区：保存tid0原掩码并绑定目标大核
每帧离开并行区：恢复tid0为CPU0-7
```

该方案虽然能让tid0在并行区外恢复CPU0-7，但RK3588S上反复修改亲和性和迁核使`core_p95`上升到约15 ms，性能不可接受。

最终改为每个OpenMP线程首次参与时绑定一次并保持。这样既隔离其他中间件线程，也避免每帧亲和性系统调用。

#### 1.2.4 CPU顺序规则

CPU数组顺序就是OpenMP tid到CPU的映射顺序。tid0还会继续执行并行区后的点云合并、Voxel、`pcl::toROSMsg()`和`publish()`，因此第一个CPU必须是大核。

推荐配置：

| 测试模式 | 线程数 | CPU顺序 |
|---|---:|---|
| 1/大核 | 1 | `{7}` |
| 2/大核 | 2 | `{6},{7}` |
| 4/大核 | 4 | `{4},{5},{6},{7}` |
| 6/混合 | 6 | `{4},{5},{6},{7},{2},{3}` |
| 8/全核 | 8 | `{4},{5},{6},{7},{0},{1},{2},{3}` |

6核和8核将大核排在前面不能消除小核造成的OpenMP barrier等待，但能避免tid0以及后续串行阶段落在小核。

#### 1.2.5 公平测试要求

1. 所有版本使用同一个固定rosbag片段和相同播放速率。
2. V2与V3分别重新启动节点，不能在一次进程中混合统计。
3. V3日志必须满足`actual_threads == requested_threads`和`affinity_ok=true`。
4. 每组正式记录1000样本，并记录`core_p95`、`voxel_p95`和`callback_p95`。
5. 6核、8核结果主要用于展示RK3588S大小核不对称和内存竞争，不预设线程越多越快。

## 二、逻辑方案对应的代码方案

### 2.1 简洁方案

修改三个文件：

1. `src/rgbd_bringup/launch/perception.launch.py`
   - 解析`projection_omp_places`为CPU整数数组。
   - 将数组通过`projection_openmp_cpus`传给节点。
   - 删除`OMP_PLACES`，将`OMP_PROC_BIND`设置为`FALSE`。
2. `src/rgbd_bringup/config/perception.yaml`
   - 删除V2/V3模式、线程数和NEON开关，避免参数文件覆盖launch命令。
3. `src/rgbd_pcl/src/cloud_workspace_node.cpp`
   - 声明并校验`projection_openmp_cpus`。
   - 删除并行指令中的`proc_bind(close)`。
   - 在并行区内使用`sched_setaffinity()`绑定当前OpenMP线程。
   - 使用`thread_local`记录已绑定CPU，避免每帧重复绑定。
   - 记录目标CPU、实际CPU和系统调用错误，生成`affinity_ok`。

### 2.2 详细方案

#### 2.2.1 Launch参数与环境

launch继续使用用户熟悉的参数：

```text
projection_enable_openmp
projection_openmp_threads
projection_omp_places
```

`projection_omp_places`由launch解析为`place_cpus`，并验证：

```text
CPU数量 == projection_openmp_threads
每个place只能包含一个CPU
线程数范围为1～16
OpenMP与NEON不能同时启用
```

传给节点的参数：

```python
{
    'projection_enable_openmp': projection_enable_openmp,
    'projection_openmp_threads': projection_openmp_threads,
    'projection_openmp_cpus': place_cpus,
    'projection_enable_neon': projection_enable_neon,
}
```

启动环境只保留：

```python
{
    'OMP_DYNAMIC': 'FALSE',
    'OMP_PROC_BIND': 'FALSE',
}
```

显式设置`OMP_PROC_BIND=FALSE`可以覆盖终端可能遗留的绑定环境，确保libgomp不会在进程启动时绑定初始线程。

#### 2.2.2 C++参数校验

节点新增：

```cpp
declare_parameter<std::vector<int64_t>>(
  "projection_openmp_cpus", std::vector<int64_t>{});
```

启动时检查：

```text
CPU编号 >= 0
CPU编号 < CPU_SETSIZE
CPU编号不能重复
启用OpenMP时CPU数量必须等于请求线程数
```

校验失败直接抛出`std::invalid_argument`，防止生成线程数正确但绑定错误的无效性能数据。

#### 2.2.3 OpenMP并行区绑定

并行指令改为：

```cpp
#pragma omp parallel num_threads(requested_threads) default(none) shared(...)
```

删除：

```cpp
proc_bind(close)
```

每个团队线程执行：

```cpp
static thread_local int bound_compute_cpu = -1;

if (bound_compute_cpu != target_cpus[tid]) {
  cpu_set_t compute_affinity;
  CPU_ZERO(&compute_affinity);
  CPU_SET(target_cpus[tid], &compute_affinity);

  if (sched_setaffinity(0, sizeof(compute_affinity), &compute_affinity) == 0) {
    bound_compute_cpu = target_cpus[tid];
  }
}
```

`sched_setaffinity()`中的`pid=0`表示只修改当前调用线程，不修改整个进程的其他线程。

#### 2.2.4 亲和性验证日志

第一帧记录：

```text
OMP_AFFINITY requested=4 actual=4 manual_cpus=4,5,6,7
OMP_AFFINITY tid=0 target_cpu=4 cpu=4 set_error=0
OMP_AFFINITY tid=1 target_cpu=5 cpu=5 set_error=0
OMP_AFFINITY tid=2 target_cpu=6 cpu=6 set_error=0
OMP_AFFINITY tid=3 target_cpu=7 cpu=7 set_error=0
```

满足以下条件才设置`affinity_ok=true`：

```text
actual_threads == requested_threads
每个tid的sched_setaffinity返回成功
每个tid的sched_getcpu结果等于目标CPU
```
