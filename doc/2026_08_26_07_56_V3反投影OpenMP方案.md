# V3：V2 标量融合链路 + OpenMP 方案（NEON关闭）

本文规划 `cloud_workspace_node` 的 V3 OpenMP 优化。V3 以 V2 的“射线缓存 + 反投影/逐点TF/ROI单遍融合”为基础，只并行融合核心，不启用 NEON，不改动 VoxelGrid、ROS消息转换、QoS和业务参数。

当前基准数据：

| 版本 | Core p95 | Voxel p95 | Callback p95 |
|---|---:|---:|---:|
| V0 原始多遍处理 | 9.385 ms | 5.695 ms | 15.200 ms |
| V1 射线缓存 | 8.877 ms | 5.515 ms | 14.286 ms |
| V2 标量遍历融合 | 4.272 ms | 6.408 ms | 10.859 ms |

V3 的直接对照基线是 V2。V3 测试期间必须保持：

```yaml
projection_enable_openmp: true
projection_enable_neon: false
```

## 一、逻辑方案

### 1.1 详细方案

#### 1.1.1 优化目标

并行 V2 已经融合好的单次深度遍历：

```text
按stride读取深度
→ 深度有效性过滤
→ 射线缓存反投影
→ 逐点Transform
→ x/z ROI
→ 写出ROI点
```

OpenMP 只负责把采样图像的行区间分配给多个CPU线程。每个线程独立读取深度图、只读射线缓存与TF矩阵，并写入自己的私有点云。并行结束后，由回调线程按原始行顺序合并私有点云，形成唯一的 `cloud_roi`。

V3 目标数据流：

```text
ROS深度回调（单线程）
  ↓ 每帧查询一次TF
准备只读参数、射线缓存、矩阵系数
  ↓
OpenMP并行区
  ├── 线程0：连续行块0 → 私有点云0
  ├── 线程1：连续行块1 → 私有点云1
  ├── ...
  └── 线程N：连续行块N → 私有点云N
  ↓ barrier
主回调线程按线程编号有序合并
  ↓
cloud_roi
  ↓
原有单线程VoxelGrid
  ↓
PointCloud2转换与发布
```

#### 1.1.2 为什么按行并行

当前深度图按行连续存储，外层循环是采样行 `vi/v`，内层循环是采样列 `ui/u`。按连续行块分配具有以下优点：

- 每个线程访问连续的深度内存，缓存局部性好；
- `ray_x_` 被各线程只读复用，`ray_y_` 按各自行区间读取；
- 每个采样行的工作量上限相同，静态划分开销小；
- 不需要逐点任务调度；
- 按线程编号合并连续行块时，可以保持V2原来的行优先点顺序；
- 为后续 V5“线程间OpenMP、线程内NEON”保留清晰结构。

V3 不使用逐点 `schedule(dynamic)`。动态调度会增加调度开销并破坏稳定顺序；当前每个采样像素至少都要读取和判断深度，连续静态行块通常足够均衡。

#### 1.1.3 输出并发策略

禁止多个线程直接调用：

```cpp
cloud_roi.push_back(point);
```

共享 `std::vector/PCL PointCloud` 的 `push_back()` 会同时修改 `size/capacity/data`，产生数据竞争、内存破坏和随机崩溃。

V3 采用线程私有输出：

```text
thread_clouds[0]
thread_clouds[1]
...
thread_clouds[N-1]
```

每个OpenMP线程只写自己的容器。并行区结束后：

1. 统计所有线程输出点数；
2. `cloud_roi.reserve(total_points)`；
3. 按线程编号从小到大合并；
4. 设置 `width/height/is_dense`。

不采用以下方案：

- `#pragma omp critical` 包围共享 `push_back()`：锁竞争会抵消并行收益；
- 每个点用 `atomic` 获取输出下标：原子热点明显且输出顺序不稳定；
- 多线程写PCL共享容器但提前 `reserve()`：`reserve()` 不能使并发 `push_back()` 安全。

#### 1.1.4 确定性划分与合并

在并行区内取得实际线程数 `team_size`，线程 `tid` 处理：

```text
vi_begin = sampled_rows * tid / team_size
vi_end   = sampled_rows * (tid + 1) / team_size
```

这是连续、不重叠、完整覆盖的行区间。线程内仍按 `vi`、`ui` 递增处理；主线程按 `tid=0..team_size-1` 合并。因此在相同输入和线程数下，输出顺序确定，并与V2行优先顺序一致。

实际分区必须使用 `omp_get_num_threads()` 返回的实际团队规模，不能假定运行时一定创建了请求线程数。

#### 1.1.5 线程私有缓冲区生命周期

推荐为每个线程维护符合PCL/Eigen对齐要求的私有点容器，例如：

```text
std::vector<CloudT::Ptr> omp_thread_clouds_
```

或使用 `CloudT::VectorType`，不要随意改用可能缺少对齐分配器的容器类型。

缓冲区策略：

- 在线程数或采样尺寸变化时调整缓冲区数量和容量；
- 每帧并行前由主线程 `clear()`；
- 按线程负责的最大采样点数在并行区外 `reserve()`；
- 并行区内只执行不会扩容的 `push_back()`；
- 下一帧复用已分配容量，避免每帧重复分配。

为了区分“数据结构变化开销”和“真正多线程收益”，V3必须额外测试 OpenMP 1线程。OpenMP 1线程包含线程私有缓冲与合并成本，是评估并行框架固定开销的控制组。

#### 1.1.6 并行区外准备

以下工作必须在进入OpenMP并行区前完成：

- 检查 CameraInfo、图像宽高和 `depth.data`；
- 检查 `16UC1/mono16/32FC1` 编码与 `step`；
- 调用 `ensureRayCache()`，禁止并行区内重建缓存；
- 查询一次 TF；
- 提取3×4变换矩阵系数；
- 读取 stride、深度范围和ROI参数；
- 准备线程私有缓冲区；
- 确认线程数有效。

并行区内禁止：

- ROS参数查询；
- TF查询；
- ROS日志；
- 修改 `camera_info_`、`ray_x_`、`ray_y_`；
- 写共享点云；
- 依赖异常处理完成正常控制流。

#### 1.1.7 RK3588S大小核策略

RK3588S属于异构大小核平台。V3不能只写“8线程最快”，必须先在实际板子读取每个逻辑CPU的容量或最高频率，再确定大核编号，禁止在代码或文档中未经验证地硬编码CPU编号。

板端识别建议：

```bash
lscpu -e=CPU,ONLINE,MAXMHZ

for cpu_path in /sys/devices/system/cpu/cpu[0-9]*; do
  cpu_name=$(basename "$cpu_path")
  capacity=$(cat "$cpu_path/cpu_capacity" 2>/dev/null)
  max_freq=$(cat "$cpu_path/cpufreq/cpuinfo_max_freq" 2>/dev/null)
  echo "$cpu_name capacity=$capacity max_freq=$max_freq"
done
```

根据实际结果确定“大核列表”和“小核列表”。OpenMP实验至少覆盖：

| 实验 | 线程数 | 亲和性 | 目的 |
|---|---:|---|---|
| V2 | 无OpenMP | 默认/固定基准 | 标量基线 |
| V3-1T | 1 | 一个已确认大核 | 测OpenMP框架固定开销 |
| V3-2T | 2 | 两个已确认大核 | 测小规模并行 |
| V3-4T | 4 | 四个已确认大核 | 主要候选配置 |
| V3-6T | 6 | 大核+小核 | 观察异构负载不均 |
| V3-8T | 8 | 全核 | 观察最大并发和带宽竞争 |

大核编号确认后，受控测试可使用：

```bash
OMP_DYNAMIC=FALSE \
OMP_PROC_BIND=TRUE \
OMP_PLACES=cores \
taskset -c <已确认的大核列表> \
ros2 launch rgbd_bringup perception.launch.py ...
```

`taskset`约束整个节点进程，`OMP_PROC_BIND/OMP_PLACES`约束OpenMP工作线程。正式记录必须写明线程数、CPU集合、调频策略和环境变量。

由于连续静态行块工作量相近，但大小核速度不同，混合大小核时慢核可能决定barrier完成时间。6线程或8线程不一定比4个大核更快，这是V3必须实测的项目亮点。

#### 1.1.8 OpenMP运行策略

要求：

- 使用显式 `num_threads(projection_openmp_threads_)`；
- 禁止OpenMP动态调整团队规模，确保重复实验可解释；
- 启动时打印请求线程数和运行时实际线程数；
- V3不启用嵌套OpenMP；
- 不在代码中全局改变其他PCL算法的线程行为；
- OpenMP参数作为启动时参数使用，不支持运行中动态切换。

线程等待策略会影响30 Hz周期任务的唤醒延迟、CPU占用和功耗。V3主实验应固定并记录同一种策略；若后续比较 `OMP_WAIT_POLICY=ACTIVE/PASSIVE`，应作为单独实验，不能混入线程数结论。

#### 1.1.9 性能上限与预期

V2当前：

```text
core_p95     = 4.272 ms
voxel_p95    = 6.408 ms
callback_p95 = 10.859 ms
```

Core约占Callback的39%，Voxel已约占59%。因此V3即使显著降低Core，整体Callback加速也会受到未并行VoxelGrid的限制。

使用p95做近似估计：

- 若Core约2倍加速，Callback可能下降到约8.7 ms；
- 若Core约3倍加速，Callback可能下降到约8.0 ms；
- 即使Core趋近0，节点仍受Voxel、转换和发布开销限制。

上述只是规划估算，不是验收目标。OpenMP团队创建、barrier、线程私有缓冲和合并都有固定开销，而当前Core只有约4.3 ms，因此线程越多不保证越快。

#### 1.1.10 正确性验收

同一输入帧下，V2标量与V3各线程配置必须满足：

- 成功/失败返回一致；
- `roi_points`一致；
- `voxel_points`一致；
- 输出header一致；
- 点坐标顺序一致或能够建立一一对应；
- 坐标绝对误差建议不超过 `1e-5 m`；
- 不产生NaN、Inf、重复点或漏点；
- `16UC1/mono16` 与 `32FC1` 均正确；
- 1、2、4、6、8线程连续运行无崩溃和内存破坏；
- 相同线程配置重复运行结果确定。

正确性验证可以临时在同一帧执行标量和OpenMP两条路径进行比较，但正式性能测试必须只执行被测路径。

#### 1.1.11 性能评测

保持现有口径：

- Release构建；
- 同一固定rosbag、相同起点和参数；
- 前30个成功帧预热；
- 后1000个成功帧统计；
- 输出 `core_p95`、`voxel_p95`、`callback_p95`；
- 测试期间出现 rosbag starvation 则该轮作废；
- 每种线程/绑核配置至少重复3轮；
- 不运行RViz等非必要程序；
- 记录ROI输入点数与Voxel输出点数，保证工作量一致；
- 记录进程CPU占用、板端温度和频率，防止降频误导结果。

新增两个OpenMP观测字段：

```text
requested_threads
actual_threads
```

性能计算：

```text
Core加速比     = V2_core_p95 / V3_core_p95
Callback加速比 = V2_callback_p95 / V3_callback_p95
并行效率       = Core加速比 / 实际线程数
```

异构大小核场景中，并行效率只用于辅助比较，不能假设每个线程算力相同。

#### 1.1.12 V3完成标准

V3完成需要同时满足：

- V2融合算法语义不变；
- OpenMP只并行Core，NEON保持关闭；
- 没有共享 `push_back()`、锁热点或逐点原子操作；
- 实际线程数可验证；
- 标量与各线程配置结果一致；
- 找到RK3588S上可复现的最优或折中线程配置；
- Core p95相对V2获得超出多轮波动范围的下降；
- Callback p95、CPU占用和温度没有因过度并行产生不可接受退化；
- 若OpenMP没有净收益，如实记录固定开销和Voxel瓶颈，不以线程数代替性能证据。

### 1.2 简洁方案

V3保留V2的单遍融合算法，把采样深度图按连续行块分给OpenMP线程。每个线程只读Depth、射线缓存和TF矩阵，写入自己的PCL对齐私有点云；并行结束后主线程按线程编号合并，从而避免共享 `push_back()`、锁和原子竞争，并保持输出顺序确定。

只并行反投影+逐点TF+ROI，VoxelGrid、消息转换和发布保持不变，NEON关闭。分别测1、2、4、6、8线程，并在板端确认实际大小核编号后测试大核绑核与全核配置。沿用1000帧 `core/voxel/callback p95`，同时记录实际线程数、CPU占用、温度和点数一致性。

## 二、逻辑方案对应的代码方案

### 2.1 详细方案

#### 2.1.1 CMake启用OpenMP

在 `src/rgbd_pcl/CMakeLists.txt` 中增加：

```cmake
find_package(OpenMP REQUIRED)
```

只为 `cloud_workspace_node` 链接OpenMP：

```cmake
target_link_libraries(
  cloud_workspace_node
  ${PCL_LIBRARIES}
  OpenMP::OpenMP_CXX
)
```

V3阶段不为 `pcl_obstacle_node` 增加OpenMP逻辑；RANSAC并行属于另一项任务。`REQUIRED`使缺少OpenMP支持时构建直接失败，避免参数显示开启但实际仍运行标量代码。

#### 2.1.2 头文件与启动校验

在 `cloud_workspace_node.cpp` 增加：

```cpp
#include <omp.h>
#include <stdexcept>
```

构造阶段：

- 校验 `projection_openmp_threads >= 1`；
- 校验请求线程数不超过项目设定的合理上限；
- V3若检测到 `projection_enable_neon=true`，直接报错，防止错误标记成OpenMP+NEON；
- 禁用OpenMP动态团队调整，或要求运行环境固定 `OMP_DYNAMIC=FALSE`；
- 日志打印OpenMP是否开启、请求线程数、NEON关闭状态。

不要默默把非法线程数改成默认值，否则评测配置无法复现。

#### 2.1.3 保留V2标量实现并增加调度入口

保留：

```cpp
depthToWorkspaceScalar(...)
```

新增：

```cpp
bool depthToWorkspaceOpenMP(
  const sensor_msgs::msg::Image & depth,
  const Eigen::Affine3d & transform,
  CloudT & cloud_roi);
```

回调中的Core路径改为：

```cpp
bool ok = false;
if (projection_enable_openmp_) {
  ok = depthToWorkspaceOpenMP(*msg, transform, *cloud_roi);
} else {
  ok = depthToWorkspaceScalar(*msg, transform, *cloud_roi);
}
if (!ok) {
  return;
}
```

这样同一个Release二进制可以通过YAML切换V2/V3，避免不同构建产物造成额外变量。

#### 2.1.4 OpenMP函数的串行准备阶段

`depthToWorkspaceOpenMP()` 进入并行区前完成与V2相同的：

1. 读取stride、深度范围和ROI参数；
2. 检查内参；
3. 检查图像宽高和data；
4. 调用 `ensureRayCache()`；
5. 校验图像编码和step；
6. 提取变换矩阵12个系数；
7. 计算 `sampled_rows=ray_y_.size()` 和 `sampled_cols=ray_x_.size()`；
8. 准备线程私有点云。

参数和矩阵可以放入函数局部只读变量，并在OpenMP并行区中通过 `shared` 使用。并行区内不得调用 `get_parameter()` 或 `ensureRayCache()`。

#### 2.1.5 线程私有点云成员

增加成员：

```cpp
std::vector<CloudT::Ptr> omp_thread_clouds_;
int omp_actual_threads_{0};
```

增加准备函数，例如：

```cpp
void prepareOpenMPBuffers(
  int requested_threads,
  size_t sampled_rows,
  size_t sampled_cols);
```

准备逻辑在并行区外执行：

- 数量不足时创建新的 `CloudT`；
- 每帧对所需容器执行 `clear()`；
- 按该线程可能负责的行数预留容量；
- 不在并行区中调整 `omp_thread_clouds_` 自身大小；
- 不允许两个线程写同一个 `CloudT`。

缓冲复用会改变一次性分配行为，因此OpenMP 1线程必须作为控制组，完整计时清空、并行、合并等固定成本。

#### 2.1.6 OpenMP并行骨架

推荐骨架：

```cpp
int actual_threads = 0;

#pragma omp parallel \
  num_threads(projection_openmp_threads_) \
  default(none) \
  shared(actual_threads, depth, sampled_rows, sampled_cols, stride, /* 只读参数和缓存 */)
{
  const int tid = omp_get_thread_num();

#pragma omp single
  {
    actual_threads = omp_get_num_threads();
  }

#pragma omp barrier

  const int team_size = actual_threads;
  const size_t vi_begin = sampled_rows * static_cast<size_t>(tid) /
    static_cast<size_t>(team_size);
  const size_t vi_end = sampled_rows * static_cast<size_t>(tid + 1) /
    static_cast<size_t>(team_size);

  CloudT & local_cloud = *omp_thread_clouds_[static_cast<size_t>(tid)];

  for (size_t vi = vi_begin; vi < vi_end; ++vi) {
    const int v = static_cast<int>(vi) * stride;
    // 获取row，按ui递增处理；只向local_cloud写入
  }
}
```

说明：

- 伪代码中的 `default(none)` 用于迫使实现者明确共享/私有变量，降低误共享风险；
- `single` 自带隐式barrier时可省略额外barrier，正式实现避免重复同步；
- 行区间计算必须使用实际线程数；
- `tid`、循环索引和临时坐标均为线程私有；
- Depth、矩阵系数、参数和射线缓存均为只读共享；
- 每个线程只写 `omp_thread_clouds_[tid]`。

`16UC1/mono16` 与 `32FC1` 在进入并行区前确定分支，避免每个像素反复判断编码。两条路径必须保持V2相同的深度单位和过滤条件。

#### 2.1.7 有序合并

并行区结束后由回调线程执行：

```cpp
size_t total_points = 0;
for (int tid = 0; tid < actual_threads; ++tid) {
  total_points += omp_thread_clouds_[tid]->size();
}

cloud_roi.clear();
cloud_roi.reserve(total_points);

for (int tid = 0; tid < actual_threads; ++tid) {
  const auto & points = omp_thread_clouds_[tid]->points;
  cloud_roi.points.insert(
    cloud_roi.points.end(), points.begin(), points.end());
}

cloud_roi.width = cloud_roi.size();
cloud_roi.height = 1;
cloud_roi.is_dense = true;
```

合并时间必须包含在 `core_ms` 中，因为它是OpenMP方案为了生成最终点云所必需的成本。

如果 `insert()` 出现对齐或类型问题，应使用 `CloudT::VectorType` 或PCL提供的同类型点容器，不能通过关闭Eigen对齐规避问题。

#### 2.1.8 计时与版本日志

保持现有Core计时边界包围完整调度函数：

```cpp
const auto core_begin = std::chrono::steady_clock::now();
depthToWorkspaceOpenMP(...);  // 包括准备、并行和合并
const auto core_end = std::chrono::steady_clock::now();
```

Voxel与Callback计时不变。性能日志标签改为能够识别模式和线程数，例如：

```text
PERF V3_OMP requested_threads=4 actual_threads=4 samples=1000
core_p95=... voxel_p95=... callback_p95=...
```

标量开关关闭时可以保留 `PERF V2_SCALAR` 标签，避免日志与实际路径不一致。实际线程数首次确定或发生变化时输出一次INFO日志，不能逐帧打印。

#### 2.1.9 NEON关闭保证

V3配置必须为：

```yaml
projection_enable_openmp: true
projection_enable_neon: false
```

V3代码不得：

- 包含ARM NEON intrinsic；
- 新增 `-march` 或NEON专用编译参数来代表手写NEON版本；
- 调用未来的NEON kernel；
- 把编译器自动向量化误标为“手写NEON”。

编译器在Release模式下可能自动向量化部分标量代码，这属于编译器优化背景，不等于V4手写NEON。P4阶段再用向量化报告确认。

#### 2.1.10 配置与测试矩阵

YAML线程数依次测试：

```yaml
projection_enable_openmp: true
projection_openmp_threads: 1  # 随后改为2、4、6、8
projection_enable_neon: false
```

#### 2.1.11 验证顺序

1. CMake链接OpenMP并完成Release构建；
2. `projection_enable_openmp=false`，确认V2标量结果未回归；
3. OpenMP 1线程，与V2逐帧比较点数、坐标和顺序；
4. OpenMP 2/4/6/8线程重复正确性比较；
5. 确认实际团队规模与配置一致；
6. 在板端识别大小核编号；
7. 固定bag、参数、亲和性和环境变量；
8. 每组预热30帧、统计1000帧、重复至少3轮；
9. 出现rosbag starvation的轮次作废；
10. 汇总加速比、CPU占用、温度和最优线程配置。

#### 2.1.12 风险与处理

风险一：共享点云数据竞争。

- 处理：线程私有点云，并行后单线程合并。

风险二：线程越多越慢。

- 处理：测1/2/4/6/8线程；考虑4个大核优于大小核混合；不预设8线程最优。

风险三：OpenMP固定开销超过收益。

- 处理：用1线程控制组量化并行区、缓冲和合并成本；Core只有4.272 ms，接受“OpenMP收益有限”的真实结论。

风险四：Voxel p95继续波动。

- 处理：保证ROI点数、点顺序和Voxel点数一致；使用相同bag起点并做多轮交替测试。

风险五：过度占用大核影响ROS和其他节点。

- 处理：同时测完整系统CPU、回调p95和rosbag供数；最终配置不只看局部Core。

风险六：并行区内发生内存扩容。

- 处理：按线程最大输入点数在主线程预留容量，并在预热阶段建立稳定容量。

### 2.2 简洁方案

1. 在 `rgbd_pcl/CMakeLists.txt` 中查找并只给 `cloud_workspace_node` 链接 `OpenMP::OpenMP_CXX`；
2. 保留 `depthToWorkspaceScalar()`，新增 `depthToWorkspaceOpenMP()`，由 `projection_enable_openmp` 调度；
3. 并行前完成参数、编码、射线缓存和TF矩阵准备；
4. OpenMP线程按实际团队规模获得连续采样行块；
5. 每线程写独立PCL对齐点云，禁止共享 `push_back()`、critical和逐点atomic；
6. 并行后按线程编号合并，合并耗时计入Core；
7. VoxelGrid、PointCloud2转换和发布保持不变，NEON明确关闭；
8. 日志记录请求/实际线程数及 `core/voxel/callback p95`；
9. 先验证1线程与V2完全一致，再验证2/4/6/8线程；
10. 在板端识别大小核编号，比较大核绑核与全核配置；
11. 每组固定bag测试1000帧并重复至少3轮；
12. 根据Callback p95、CPU占用和温度共同选择最终线程数。
