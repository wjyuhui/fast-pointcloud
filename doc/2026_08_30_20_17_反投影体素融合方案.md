# 反投影、Transform、ROI 与 Voxel 融合方案

> 状态：设计方案，暂不修改实现  
> 目标平台：RK3588S / ROS2 Humble / C++17 / OpenMP / AArch64 NEON  
> 当前固定回归配置：1280×720 深度图、`depth_stride=2`、`voxel_leaf_m=0.05`、固定 rosbag 片段

## 一、逻辑方案

### 1.1 简洁方案

当前链路先生成约 16 万个 ROI 点，再调用 PCL VoxelGrid 将其降为约 8500 个体素中心：

```text
深度图
  → 反投影
  → Transform
  → ROI过滤
  → 中间 cloud_roi（约16万点）
  → PCL VoxelGrid再次遍历
  → cloud_voxel（约8500点）
```

融合后的链路不再生成 `cloud_roi`：

```text
深度图
  → 反投影 + Transform + ROI
  → 直接计算体素键
  → 累加 sum_x / sum_y / sum_z / count
  → 输出体素中心 cloud_voxel（约8500点）
```

OpenMP 模式下，每个线程维护独立的体素累加表，像素循环内不使用锁和原子操作；并行区结束后，只合并各线程实际占用的体素，而不再合并约 16 万个中间点。

实施顺序：

1. 保留当前 V2/V3/V4 路径作为回归基准。
2. 先实现标量融合版本，验证与 PCL VoxelGrid 的输出语义一致。
3. 再实现 OpenMP 线程局部体素表和负载均衡。
4. 最后根据 Profiling 决定是否对融合循环加入 NEON。

第一阶段不追求与 PCL 输出点顺序一致，只要求体素集合、体素数量和质心在容差内一致。

### 1.2 详细方案

#### 1.2.1 当前问题

当前 `cloud_workspace_node` 的核心处理包含两个连续算子：

1. `depthToWorkspace*()`：反投影、坐标变换、ROI过滤，生成 `cloud_roi`。
2. `pcl::VoxelGrid<PointT>`：再次遍历 `cloud_roi`，生成 `cloud_voxel`。

当前固定包在 `stride=2` 时每帧处理 230400 个采样像素，约 16 万个点进入 `cloud_roi`，Voxel 后约剩 8500 点。因此中间点云的数据量远大于最终输出，且当前 V3 还会先写线程局部点云，再复制到 `cloud_roi`。

主要冗余包括：

- 约 16 万个 `PointXYZ` 的中间存储；
- V3 线程局部点云到 `cloud_roi` 的二次复制；
- PCL VoxelGrid 对约 16 万个点的再次读取；
- `cloud_roi` 和 `cloud_voxel` 的独立分配及缓存流量；
- OpenMP 连续行切分导致的有效点数量不均衡。

#### 1.2.2 融合算子的语义

对于每个通过深度范围与工作空间 ROI 检查的目标坐标点 `(x, y, z)`，按照叶子尺寸 `leaf` 计算体素坐标：

```text
ix = floor(x / leaf)
iy = floor(y / leaf)
iz = floor(z / leaf)
```

同一 `(ix, iy, iz)` 下累计：

```text
sum_x += x
sum_y += y
sum_z += z
count += 1
```

处理完成后输出体素质心：

```text
centroid_x = sum_x / count
centroid_y = sum_y / count
centroid_z = sum_z / count
```

体素索引必须使用与 PCL VoxelGrid 一致的全局原点量化方式，不能简单改成相对 ROI 最小值的索引，否则 ROI 最小值不与叶子尺寸对齐时，体素边界会发生变化。

#### 1.2.3 数据结构选择

首选“线程局部、持久化、开放寻址体素表”，不在像素热循环中使用 `std::unordered_map`、互斥锁或共享原子累加。

每个槽位包含：

```text
VoxelKey key
double sum_x
double sum_y
double sum_z
uint32 count
uint32 generation
```

设计原则：

- 表容量在预热阶段确定，后续帧复用，不进行逐帧堆分配；
- 使用开放寻址解决冲突；
- 使用 `generation` 或已占用索引列表进行逻辑清空，避免每帧清零整个哈希表；
- 记录 `occupied_slots`，合并时只遍历实际使用的槽位；
- 使用 64 位体素键，避免三个整数结构体带来的额外比较和填充；
- 对体素索引范围做显式检查，防止打包溢出。

64 位键可使用三个带偏移的有符号 21 位索引：

```text
key = pack(ix, iy, iz)
```

21 位有符号范围在 5 cm 叶子下已远大于室内机器人工作空间。实现时必须集中封装 `packVoxelKey()`，禁止在循环中散落位运算。

#### 1.2.4 标量融合版本

先实现单线程标量融合版本，目的不是最终性能，而是建立可信的正确性基准：

```text
for 每个采样深度像素:
    检查深度合法性
    反投影并Transform
    检查ROI
    计算voxel key
    更新全局体素累加表

遍历已占用体素:
    计算质心并写入cloud_voxel
```

该版本应与现有“V2 Scalar + PCL VoxelGrid”同时存在，通过参数选择，不能直接删除原路径。

标量融合版本需要回答两个问题：

1. 自定义体素语义是否与 PCL 基线一致；
2. 去除中间点云后，即使不上 OpenMP，整体 `projection + voxel` 是否已经明显下降。

#### 1.2.5 OpenMP 融合版本

每个 OpenMP 线程持有自己的 `LocalVoxelTable`：

```text
OpenMP tid0 → local_voxels[0]
OpenMP tid1 → local_voxels[1]
OpenMP tid2 → local_voxels[2]
OpenMP tid3 → local_voxels[3]
```

像素处理阶段只更新本线程体素表：

```text
#pragma omp for schedule(static, chunk_rows)
for 每个采样行:
    for 每个采样列:
        反投影 + Transform + ROI
        local_voxels[tid].accumulate(key, x, y, z)
```

不再采用“每线程一整段连续行”的手工切分。采用较小的静态行块并循环分配，使图像上方和下方的工作混合到不同线程，减少当前固定包中 `4k / 43k / 55k / 54k` 的有效点失衡。

`chunk_rows` 初始候选为 4、8、16，必须通过固定包测试选择，不能凭经验固定。

#### 1.2.6 线程局部体素合并

第一版采用低风险的串行体素级归并：

```text
每线程约若干千个局部体素
           ↓
合并到global_voxel_table
           ↓
约8500个最终体素
```

虽然第一版仍有串行归并，但合并单位从约 16 万个点降为数千到数万个局部体素项，预计远小于当前点云复制成本。

如果 Profiling 表明体素归并仍超过目标，再进入第二版并行归并：

- 按 `hash(key) % merge_shards` 将局部体素项分片；
- 每个线程只负责一个或多个互斥分片；
- 不在单个体素上使用共享浮点原子加法；
- 每个分片完成后并行生成最终质心。

不要在第一版直接实现复杂的无锁共享哈希表，以免正确性、可维护性和调试成本超过收益。

#### 1.2.7 为什么不直接让多个线程写同一张体素表

以下方案不作为默认实现：

- 每个有效点使用互斥锁；
- 每个有效点对 `sum_x/sum_y/sum_z/count` 做原子更新；
- 每个有效点通过全局原子计数器申请输出位置；
- 在热循环中使用动态扩容的 `std::unordered_map`。

这些方案会让热点体素或共享计数器的 cache line 在 CPU 核心之间频繁迁移，在 RK3588S 大小核与共享内存系统上容易放大 p95。

#### 1.2.8 与 NEON 的关系

融合体素版本先完成标量和 OpenMP，不立即加入 NEON。

原因是体素表插入包含：

- `floor()` 与整数索引；
- 哈希；
- 分支与冲突处理；
- 不规则内存访问。

这些部分不适合直接四路 SIMD。NEON 仍可用于哈希插入之前的：

- 4 路深度转换；
- 反投影；
- Transform；
- ROI mask；
- 体素索引前的浮点缩放。

是否加入 NEON 必须根据融合版本 Profiling 决定。如果哈希累加占主导，继续优化前半段 SIMD 的收益会受 Amdahl 定律限制。

#### 1.2.9 正确性标准

融合输出与 PCL VoxelGrid 不要求点顺序一致，应按体素键比较。

固定包至少验证：

- 最终体素键集合是否一致；
- 最终体素数量是否一致；
- 每个体素的点计数是否一致；
- 每个体素质心的最大绝对误差；
- BEV 占用格集合是否一致；
- 是否出现 NaN、Inf、越界键或计数溢出。

建议验收阈值：

```text
体素键集合：完全一致
体素点计数：完全一致
质心最大绝对误差：≤ 1e-4 m
BEV占用格：完全一致；若浮点边界导致差异，必须逐格解释
```

如果 PCL 内部浮点累加顺序导致不能完全达到上述质心阈值，应先输出误差分布，再决定放宽标准，不能静默接受差异。

#### 1.2.10 性能评测标准

融合算子不能继续只使用原来的 `core_p95` 和 `voxel_p95` 解释，因为融合后两个阶段已经无法自然分开。

需要增加统一的：

```text
compute_total_p50/p95/p99
```

定义为：

```text
反投影开始 → 最终cloud_voxel生成完成
```

基线也要补同样的计时边界：

```text
V2/V3/V4：depthToWorkspace* + PCL VoxelGrid
融合版本：fusedDepthToVoxel*
```

同时保留：

```text
queue_wait_p95
callback_p95
input_sampled_pixels
roi_valid_points
occupied_voxels
local_voxel_entries
dropped_pending
```

首轮性能目标不承诺 1 ms，采用分阶段标准：

1. 标量融合必须快于或不劣于 `V2 Scalar + PCL VoxelGrid`；
2. OpenMP 融合 2 大核必须明显快于标量融合；
3. 4 大核相对 2 大核若无收益，应优先保留 2 大核给 ROS/DDS/PCL 下游线程；
4. 完整系统不能以牺牲下游 p95 和丢帧率换取单算子平均耗时。

### 2.1 简洁代码方案

src/rgbd_bringup/config/perception.yaml
src/rgbd_bringup/launch/perception.launch.py
```

新增核心类型：

struct VoxelAccum;
class FlatVoxelTable;
```

新增处理函数：

```cpp
bool depthToVoxelFusedScalar(..., CloudT & cloud_voxel);
bool depthToVoxelFusedOpenMP(..., CloudT & cloud_voxel);
```

新增模式参数，保留原路径：

```yaml
projection_fuse_voxel: false

```

执行逻辑：

```cpp
if (projection_fuse_voxel_) {

}
```

先实现标量融合和正确性回归，再实现 OpenMP，不在同一次提交中加入 NEON。

### 2.2 详细代码方案

#### 2.2.1 参数与版本隔离

在 `cloud_workspace_node` 中声明：

```cpp
declare_parameter<bool>("projection_fuse_voxel", false);
declare_parameter<bool>("projection_fused_voxel_openmp", false);
declare_parameter<int>("projection_voxel_chunk_rows", 8);
declare_parameter<int>("projection_voxel_table_capacity", 16384);
```

参数规则：

- `projection_fuse_voxel=false`：保持现有 V2/V3/V4 行为；
- `projection_fuse_voxel=true` 且 `projection_fused_voxel_openmp=false`：标量融合；
- 两者均为 `true`：OpenMP 融合；
- 第一版不允许融合 Voxel 与 NEON 同时启用，避免一次引入多个变量；
- `projection_voxel_table_capacity` 必须为 2 的幂，并设置合理上下限；
- 表容量不足时记录错误并安全回退或扩容，不能静默丢体素。

配置文件默认关闭融合功能，保证现有路径不受影响。

#### 2.2.2 新增体素数据类型

建议将实现先放在 `cloud_workspace_node.cpp` 的匿名命名空间，稳定后再拆分头文件。

```cpp
using VoxelKey = uint64_t;

struct VoxelAccum
{
  VoxelKey key{0};
  double sum_x{0.0};
  double sum_y{0.0};
  double sum_z{0.0};
  uint32_t count{0};
  uint32_t generation{0};
};
```

`FlatVoxelTable` 至少提供：

```cpp
void beginFrame();
bool accumulate(VoxelKey key, float x, float y, float z);
bool merge(VoxelKey key, const VoxelAccum & src);
size_t size() const;
const std::vector<uint32_t> & occupiedSlots() const;
const VoxelAccum & slot(uint32_t index) const;
```

实现要求：

- 禁止在 `accumulate()` 中分配内存；
- 使用线性探测或经过基准验证的轻量探测；
- 达到最大装载因子前主动扩容；
- 性能窗口内不允许发生扩容；
- 记录最大探测长度和扩容次数用于诊断；
- generation 回绕时执行一次完整清零。

#### 2.2.3 体素键函数

新增集中封装：

```cpp
bool makeVoxelKey(
  float x, float y, float z,
  float inverse_leaf,
  VoxelKey & key);
```

函数职责：

1. 使用 `floor(x * inverse_leaf)` 等方式生成有符号体素索引；
2. 检查索引是否在可打包范围内；
3. 对负索引加偏移后打包；
4. 返回失败时增加诊断计数，不写入非法键。

不要使用直接 `static_cast<int>(x * inverse_leaf)`，因为 C++ 向零截断与负坐标的 `floor()` 语义不同。

#### 2.2.4 标量融合函数

函数签名：

```cpp
bool depthToVoxelFusedScalar(
  const sensor_msgs::msg::Image & depth,
  const sensor_msgs::msg::CameraInfo & camera_info,
  const Eigen::Affine3d & transform,
  float voxel_leaf,
  CloudT & cloud_voxel);
```

内部复用现有：

- `prepareWorkspaceInputs()`；
- 射线缓存 `ray_x_ / ray_y_`；
- 深度编码检查；
- Transform 参数提取；
- 深度与 ROI 语义。

不要调用现有 `tryAppendPoint()`，因为它会创建 `PointT` 并写入中间点云。应新增返回目标坐标的标量辅助函数，或者在融合循环中直接完成验证与累加。

循环结束后：

```cpp
cloud_voxel.clear();
cloud_voxel.reserve(global_voxel_table_.size());

for (occupied slot : global_voxel_table_) {
  const auto & a = slot;
  PointT p;
  p.x = static_cast<float>(a.sum_x / a.count);
  p.y = static_cast<float>(a.sum_y / a.count);
  p.z = static_cast<float>(a.sum_z / a.count);
  cloud_voxel.push_back(p);
}
```

设置 `width/height/is_dense`，并对空输出采用与现有节点一致的错误处理。

#### 2.2.5 OpenMP 融合函数

函数签名：

```cpp
bool depthToVoxelFusedOpenMP(
  const sensor_msgs::msg::Image & depth,
  const sensor_msgs::msg::CameraInfo & camera_info,
  const Eigen::Affine3d & transform,
  float voxel_leaf,
  CloudT & cloud_voxel);
```

成员缓冲：

```cpp
std::vector<std::unique_ptr<FlatVoxelTable>> omp_local_voxel_tables_;
FlatVoxelTable global_voxel_table_;
```

准备阶段：

```cpp
for 每个实际线程:
    local_table.beginFrame()
global_table.beginFrame()
```

并行阶段建议保持现有手工亲和性方案，但简化每帧重复操作：

```cpp
#pragma omp parallel num_threads(requested_threads)
{
  const int tid = omp_get_thread_num();
  auto & table = *local_tables[tid];

  #pragma omp for schedule(static, chunk_rows)
  for (size_t vi = 0; vi < sampled_rows; ++vi) {
    // 深度 → 目标坐标 → ROI → voxel key → table.accumulate()
  }
}
```

不要在循环内写共享 `cloud_roi`，不要在每个有效点上调用原子操作。

#### 2.2.6 局部表归并与最终输出

第一版在并行区结束后由计算协调线程执行：

```cpp
for each local_table:
  for each occupied_slot:
    global_table.merge(key, accum)
```

然后遍历全局表生成 `cloud_voxel`。

必须单独计时：

```text
fused_accumulate_ms
fused_merge_ms
fused_emit_ms
fused_total_ms
```

只有当 `fused_merge_p95` 成为主要瓶颈时，才实现按 key hash 分片的并行归并。不要提前复杂化。

#### 2.2.7 `processFrame()` 分支调整

现有路径保持不变，融合路径直接返回 `cloud_voxel`：

```cpp
CloudT::Ptr cloud_voxel(new CloudT);

if (projection_fuse_voxel_) {
  if (projection_fused_voxel_openmp_) {
    ok = depthToVoxelFusedOpenMP(..., voxel_leaf, *cloud_voxel);
  } else {
    ok = depthToVoxelFusedScalar(..., voxel_leaf, *cloud_voxel);
  }
} else {
  CloudT::Ptr cloud_roi(new CloudT);
  // 保留现有 V2/V3/V4
  // 保留 PCL VoxelGrid
}
```

发布、时间戳和 `frame_id` 逻辑继续复用现有代码。

为了公平比较，应在两个分支外增加统一的 `compute_total_begin/end`，不要使用“融合算子的 total”与“旧路径的 core”直接比较。

#### 2.2.10 开发与回归步骤

1. 保存现有 V2/V3/V4 固定包结果和启动命令。
2. 增加统一 `compute_total_p95`，确认旧版本数值稳定。
3. 实现 `VoxelKey`、`VoxelAccum`、`FlatVoxelTable` 单元测试。
4. 实现标量融合版本。
5. 使用验证模式逐帧比较融合输出与 PCL VoxelGrid。
6. 标量正确后测 `V2 Scalar + PCL VoxelGrid` 对比标量融合。
7. 实现 OpenMP 线程局部体素表。
8. 测试 1 大核、2 大核、4 大核；暂不加入小核。
9. 测试 `chunk_rows=4/8/16`，记录每线程像素数、ROI有效点和局部体素数。
10. 仅在归并成为瓶颈时实现并行分片归并。
11. 完成 cloud-only 后再恢复 PCL/BEV 完整流水线，检查下游 p95 和丢帧率。
12. 最后评估是否值得加入 NEON，不默认把 OpenMP 与 NEON 同时开发。

#### 2.2.11 完成标准

代码功能完成必须同时满足：

- 默认参数仍走原路径，不破坏现有 V2/V3/V4；
- 固定包正确性达到体素键、计数和质心验收标准；
- 性能窗口内无体素表扩容；
- 无逐点锁、逐点原子和逐点动态分配；
- `actual_threads` 与CPU亲和性验证通过；
- `compute_total_p95` 优于旧路径；
- 完整系统丢帧率和下游 p95 不恶化；
- 测试报告明确区分 cloud-only 算子收益与完整ROS系统收益。
